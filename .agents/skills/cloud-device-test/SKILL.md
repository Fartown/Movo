# 云真机测试

把用户目标转成实际设备操作和可核查结果。单测、安装完成、首页显示、模型自称成功，都不能替代功能验收。

## 入口与分工

- **打开给用户看**：连接指定设备，按要求安装/启动，确认实时画面可用，保留需要的 App、配置与租约。
- **测试/验收**：范围 → 环境/配置 → 原生操作与逐步采证 → 判定/必要回归 → HTML/Markdown 报告。
- **继续/复测**：读取 scope、checkpoint 和 facts，核对当前设备、APK、配置；重试用新 run，保留旧证据。
- **只写方案**：交付方案；用户明确要求确认后执行时才等待确认。

主 agent 管范围、预期、证据审核、问题分析和交付；**实际 bytedcli、设备输入及 CDP 操作委派给一个设备执行 subagent**。委派包包含目标/约束、用例文件、证据目录、保留资源和检查点。单设备只有一个动作执行者；其他 agent 可分析代码、运行单测或审核已落盘证据，不并发点按。

依赖当前安装的 `bytedcli`（Dora 指南）、`test-workflow`（用例/事实/报告）。在 `~/.agents/skills/` 或 `~/.codex/skills/` 定位并按需读取，不复制旧版 CLI 协议。不确定参数先读当前 help。浏览器用于远控交接、授权和报告查看，读取当前浏览器 Skill；原生设备不以远控网页充当浏览器产品测试。首版支持 Android，不套用到 iOS/鸿蒙。

## 1. 固定测试范围

读取项目规则、Git/制品状态、用户范围和已有用例，写 `scope.md`：功能、case ID、可靠预期来源、环境需求、当前结果、证据位置。既有核心功能与本次改动都要考虑。仅当缺少实质性目标/判据且无法从项目取得时提问，不阻断其他独立用例。

证据放项目 `tmp/tasks/<YYYY-MM-DD>-<任务名>/`，遵守项目更具体规则。每个 case/run 单独目录。Agent App 可参考 [movo-example.md](references/movo-example.md)，不能机械套用其功能。

## 2. 环境、配置与设备

设备执行者先读 [dora-execution.md](references/dora-execution.md)。核对品牌/系统/占用/连接和租约，现有租约验证后复用，不擅自换品牌。用 `scripts/checkpoint.py` 取得 serial 对应的本机动作锁，再操作设备；锁不是平台租约，也不能约束用户或其他电脑。

确认包名、已安装版本、目标 APK SHA-256 及对应代码状态。正确的已安装 App 直接复用；修改了代码却没有对应新包，不能声称验收了当前改动。构建需 Node 时遵守项目 `.nvmrc` 与 fnm，不全局安装 Node。

模型/账号配置优先从当前 App、项目明确的受保护配置、当前会话及已定位的历史授权来源找回。已给配置直接设置并读回，不因新设备为空就判定没有 Key。密钥不进入命令回显、截图或报告。真实链路用本轮标识的 App 消息验证；HTTP 200 只说明接口探测成功。fixture 仅用于明确标记的边界场景，不替代真实账号验收。

已授权测试所需的普通安装、权限和导航直接推进；可通过 CUA 完成的平台授权直接处理。需要用户实际提供信息或无法自主通过认证时，说明已尝试内容与具体缺口。

## 3. 操作、事实与检查点

先读 [evidence-and-resume.md](references/evidence-and-resume.md)，按 test-workflow 契约冻结 case。用 `scripts/validate_evidence.py capture-env` 从当前 ADB 采集原生环境，不手填 browser 冒充原生执行器。

每步：**核对前态 → 确认真录屏已启动 → 登记未决动作 → 操作 → 等待状态并读回 → 截图核对 → 追加事实 → 完成检查点**。

- 坐标取自当前画面；语义定位需新鲜 hierarchy、唯一匹配和正确 package。命令成功/`sent` 不代表界面成功。
- 输入后核对焦点、中文/多行和键盘状态。入口用例须进入目标页并返回，按钮可见不足以判定可用。
- 工具测试核对真实调用与系统/外部读数；续聊使用未写入长期记忆的上一轮信息。
- 图片解码并看内容，视频播放检查关键动作。脚本校验文件/哈希/解码，不能代替预期判断。
- 每步即时写 facts；追加失败先保留原始事实并修复记录。发送/安装前登记 pending，恢复时先读回，不能直接重放。
- 外部输入、断连和弹窗干扰保留现场，单列环境/执行问题。已有 FAIL 不被后续阻断掩盖。

## 4. 判定、恢复和交付

沿用 test-workflow 的 PASS/FAIL/ERROR/BLOCKED/INCONCLUSIVE/NOT RUN/SKIPPED。PASS 表示可靠预期得到证据支持；人工式审查用 `manual`，标明判断者/理由，不能包装成机器断言。原生 UI 与浏览器使用相同的截图和真录屏要求，支持的原生执行器不因平台被封顶。

设备/APK/provider/数据变化需新 run，说明可比范围。旧 run 保持原样，不能删除 waiver 或改判据转成 PASS。恢复时重新验证锁、前台状态与 pending。

进度直接报告已完成/失败/阻断/未测功能及最近证据。等待传输或模型时按实际读数更新。功能执行后生成报告并运行 test-workflow 的 validate_report.py，默认不打开报告或另起浏览器巡检；报告校验不能替代产品覆盖。

复用 test-workflow 生成同源 HTML/Markdown，交付范围、结果、问题、未测项和证据。收尾只处理本任务资源，恢复临时设置，保留用户指定的 App、配置、会话与租约；停止不再需要的守护并说明到期时间。没有保留要求时才释放本轮新租设备。交接后释放本机动作锁，不清空用户配置。
