## 真机发现的延迟崩溃

r4 系统入口在短时间观察时正常，延长录像后主界面退回桌面。系统日志证明：后台广播冷启动主进程时，Application 的设置订阅立即新建唤醒词麦克风前台服务；系统拒绝其前台提升，约 102 秒后以 `ForegroundServiceDidNotStartInTimeException` 终止进程。崩溃来自 `MovoWakeWordService`，不是展示用助手入口。

r5 将应用主动创建唤醒服务延后至 Activity 可见并完成 resume；已有前台服务直接使用自身设置订阅，不重复发起前台服务启动。系统合法的 sticky 服务重启继续保留，避免修崩溃时破坏后台唤醒恢复。平台规则依据：[麦克风前台服务的后台启动限制](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start)、[Service 的 sticky 重启说明](https://developer.android.com/reference/android/app/Service)。新增回归验证后台冷入口不启动服务、页面可见后才启动。

旧包短时间通过记录与延迟崩溃证据同时保留，不能用短时间正常覆盖真实崩溃。

## 连续语音仍有一项失败

r5 的原始 `core` 用例在第二轮暗号召回处 FAIL：要求完整“蓝鲸47”，实际回答正文只有“47”。第一轮识别包含完整暗号，第一答也包含完整暗号；第二轮带 1.2 秒停顿的语音被合并成一次请求，没有重复自动发送。第二轮模型原始增量、`output_text.done`、终态正文和应用解析长度全部为 2，`answer` 与 `speech.request` 同为“47”。这能确认当前失败发生在模型正文返回处，不能归因于 TTS 截字，也不能改成通过。

证据：`device/release-r5-environment/TC-VOICE-CORE-r1/evidence/output/` 的 `events.json`、`voice-diagnostics.json` 和 `result.json`。第二请求 response id 为 `resp_02179010385999133d44b650730fd07bb29a2150d8432a017948c`；请求消息数从 8 增至 10。当前未导出原始请求全文，不把消息数或界面思考文字视为请求逐字段正确的证明。用户选定模型及思考配置保持原样；不从思考内容补正文、不静默更换模型。

原 `core` 因该失败提前停止，后续插话和口述结束不能算该轮通过。另用既有 `playback_diagnostic` 模式继续采证，保持原暗号断言，仅允许失败时继续执行后续步骤，最终仍按原断言判定。

补充诊断轮本次完整 PASS，69.06 秒、4 次自动 dispatch，第二问和插话替换的正文均为完整“蓝鲸 47”，`diagnostic_findings=[]`。句中停顿的补话合并、播报后续听、插话替换及口述结束全部执行；55.281 秒结束后继续输入负例，没有新增提交。4 条 `speech.request` 均与对应 LLM 正文逐字一致。

对替换答复额外做了离线 PCM 对照：turn 5 的 68,160 字节 owned decoder PCM 在 49.751–52.264 秒播放器窗口中完整逐字节匹配，前 20,160 字节（420 ms）及后部均全零，没有旧声前缀。证据为 `device/release-r5-environment/TC-VOICE-CORE-DIAGNOSTIC-r1/evidence/output/replacement-pcm-comparison.json`。这仅证明本轮软件音频流，不代表物理外放可懂性、AEC 双讲或插话停声延迟达标。
