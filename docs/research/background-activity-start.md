# 调研：Movo 在后台打开其他 App 界面被系统拦截（计时器 / 闹钟 / 打开 App）

状态：待决策（2026-09-27）。代码未改：`fix/clock-tool-verify` 分支（be8f2e5）的「透明窗口 + 系统核实」方案已从 `fix/ui-review` 撤回，分支保留备查。

## 1. 现象

用户在小米手机上让 Movo「设一个计时器」，Movo 说设好了，时钟里实际没有。同类问题也出现在 `launch_app`（打开 App）：被拦截时仍报「已启动」。

## 2. 根因（真机实证，红米 K80 Pro / HyperOS 2 / Android 15）

Movo 设计时器的做法是在后台服务里 `startActivity(ACTION_SET_TIMER)`，交给时钟 App 处理；`startActivity` 不抛异常就回报成功。但「后台启动界面」有两层拦截，被拦时都**不会抛异常**：

| 层 | 条件 | 日志 | 结果 |
|---|---|---|---|
| 小米「后台弹出界面」权限（系统设置 → 应用 → Movo → 其他权限） | 未授权，且 Movo 屏幕上没有可见窗口 | `MIUILOG- Permission Denied Activity … SET_TIMER` → `Abort background activity starts from 10366` → `(BAL_ALLOW_PERMISSION) result code=102` | 被丢弃，Movo 报成功 |
| 安卓原生后台启动限制（BAL） | 无障碍服务未绑定，且没有可见窗口 | `Background activity launch blocked! … callingUidHasAnyVisibleWindow: false` → `(BAL_BLOCK) result code=102` | 被丢弃，Movo 报成功 |
| 放行 | Movo 有可见窗口（App 在前台、对话浮层、悬浮球） | `(BAL_ALLOW_VISIBLE_WINDOW) result code=0` | 时钟直接开始计时 |

要点：

- 安卓原生规则把「由系统绑定的无障碍服务」列为豁免之一，所以无障碍开着时，原生这层是放行的（日志里的 `BAL_ALLOW_PERMISSION`）。真正拦住的是**小米自己加的「后台弹出界面」**。
- 默认开着的**常驻悬浮球**本身就是可见窗口，所以大多数情况下能设上。能复现的失败组合是：常驻悬浮球关 + 「后台弹出界面」未授权 + Movo 不在前台。
- 不是时钟不支持：同样的 intent 在前台发，小米时钟会直接开始计时。

证据：`.docs/clock-tool-verify/logcat_before_bg_miuideny.txt`、`logcat_after_blocked.txt`、`logcat_after_fg_timer.txt`，截图 44 / 45（bug）。

## 3. 可选方案

### A. 保持现状
- 做法：不改。
- 好：零成本。
- 坏：上述组合下继续「说设好了、实际没设」，用户信任受损。

### B. 如实措辞（不核实、不绕过）
- 做法：工具结果从「已创建」改成「已发给时钟，系统没有回执」，并在工具说明里要求模型对用户只说「已让时钟去设，建议看一眼时钟确认」，不说「设好了」。
- 好：改动极小、诚实，不依赖任何厂商行为。
- 坏：每次都多一句不确定的话；真正失败时用户仍要自己发现。

### C. 引导开启「后台弹出界面」权限
- 做法：在「设置 → 权限」的必要权限里，小米系列（小米 / 红米 / POCO）加一行「后台弹出界面」，点了跳到系统的 Movo 权限页；开启前在工具失败说明里同样提示。
  - 检测是否已开启：小米没有公开 API。常见做法是读 AppOps 的小米私有 op（10021）——**属于读取未公开接口，可能随系统版本失效**。也可以不检测，只做「去开启」入口加一句说明。
- 好：把问题交给正规的系统权限，一次开启长期有效；和现有「悬浮窗 / 无障碍」权限引导同一套体验。
- 坏：多一个权限项（小米机型）；检测不可靠时只能常驻提示。

### D. 只在 Movo 有真实可见界面时发起
- 做法：打开时钟 / 打开 App 这类动作，只在 Movo 确实有可见界面时执行（App 在前台、对话浮层开着、悬浮球显示着）；否则不发起，直接告诉模型「现在无法在后台打开其他 App 界面」，由模型请用户打开 Movo 或开启权限。
- 与被否掉的「1 像素透明窗口」的区别：不为了放行而造窗口，只利用用户本来就看得到的界面。
- 好：行为可预期，永远不会「静默失败却报成功」。
- 坏：常驻悬浮球关掉的用户，在后台时这类动作直接做不了。

### E. Movo 自己实现计时器 / 闹钟（不依赖时钟 App）
- 做法：用 `AlarmManager.setAlarmClock` 在 Movo 内部定时，到点由 Movo 响铃 / 全屏提醒（前台服务 + 通知），不再打开系统时钟。
- 好：不涉及后台启动界面，任何系统都可靠；结果完全可知。
- 坏：闹钟不出现在系统时钟 App 里（用户习惯差异）；需要精确闹钟权限（Android 14 起新装默认不给 `SCHEDULE_EXACT_ALARM`，闹钟类应用可声明 `USE_EXACT_ALARM`，上架审核有要求）；要做响铃、稍后提醒、关闭等整套体验。

### F. 决定变更（2026-10-03，用户指示「保准确性」后）
- **此前否决、现已采纳**：保留 1 像素透明窗口以让后台/语音/锁屏下的闹钟真正派发成功（小米无可见窗口时后台 startActivity 会被静默丢弃，见本文第 2 节与 be8f2e5 实证）。采纳理由：当初否决是担心「绕过系统又谎报成功」；现在配合下方的准确核实，透明窗口只负责「让它真设上」，不负责「谎报」。
- **核实方式升级**：不再看「下一次闹钟」（会被日历 0 点占住，核不准）。改为归因到本次创建：有 Root 用 `dumpsys alarm` 匹配本次请求的 HH:MM/时长新出现的 ALARM_ALERT/TIMER_ALERT；无 Root 用 `getNextAlarmClock()` 匹配本次请求时刻。匹配到→已验证；匹配不到→报 `unknown`「已提交，未能确认」，绝不谎报已设。
- 仍然否决：让模型以为「说了就一定设好」而不做任何核实。

## 4. 建议

组合 **B + C**：先改措辞，保证不再「说设好了」；再在小米机型上加「后台弹出界面」权限引导（不做私有接口检测，只给入口加说明）。`launch_app` 同样适用 B + C。

如果希望计时器 / 闹钟「说了就一定生效」，再单独评估 **E**（工作量最大，体验要重新设计）。
