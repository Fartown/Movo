## 1. 为什么需要这个功能

Movo 的任务可能失败、卡住或者很慢。原因可能出在模型服务（限流、额度、登录失效、返回异常）、网络（断网、切换网络、DNS 失败）、系统（切到后台被断网或冻结、前台服务被拒、进程被杀），也可能出在工具执行上。用户在对话里只能看到「失败了」或「一直在转」，无从判断原因，也不知道该怎么办。

运行日志要解决两件事：
1. 让用户自己弄清楚一次任务出了什么问题、该怎么办；
2. 在需要反馈时，一键拿出足够完整、又不含隐私的证据。

## 2. 谁在用、什么时候用

| 使用者 | 典型时刻 | 想要的结果 |
|---|---|---|
| 普通用户 | 任务失败、一直没反应、明显很慢 | 用人话说清楚原因，以及下一步怎么做（换网络、重新登录、检查额度、稍后再试） |
| 普通用户 | 想反馈问题 | 一键导出一份可以直接发出去的记录 |
| 开发者（你） | 复现、定位问题 | 精确的阶段耗时、错误码、重试链路、服务端请求 ID，以及当时的设备状态 |

## 3. 必须回答的五个问题

这个功能的全部价值就是回答下面五个问题，答不出来就算没做好。

| # | 问题 | 必须给出的答案 | 例子 |
|---|---|---|---|
| Q1 | 这次任务为什么失败？ | 失败原因（人话 + 错误码）、失败发生在哪一步、建议怎么做 | 「模型接口限流（HTTP 429），已自动重试 3 次仍失败。建议稍后再试或换模型」 |
| Q2 | 为什么这么慢？ | 总时长分别花在了哪里：等模型开始回答、接收回答、执行工具、重试等待、上下文压缩 | 「共 18 秒：等模型首字 11 秒，接收 4 秒，工具 2 秒，重试等待 2 秒」 |
| Q3 | 现在卡在哪？（任务进行中） | 当前在哪一步、已等了多久、距离上次收到数据多久 | 「第 2 轮 · 等待模型回复 · 已 45 秒，一直没有收到数据」 |
| Q4 | 当时手机上发生了什么？ | 任务进行期间的网络变化、切前后台、前台服务启停、进程重启 | 「第 12 秒网络从 Wi‑Fi 切到移动数据，随后请求中断」 |
| Q5 | 怎么把问题交给开发者？ | 导出单个任务或全部记录，包含上面所有结论、设备与版本信息，不含隐私 | 一个 Markdown 文件，也可以复制 |

## 4. 信息模型

以「任务」为单位组织日志，而不是按事件平铺。

```
任务（一次发送 → 最终回复，编号 R1、R2…）
├─ 结论：成功 / 失败 / 已停止 / 进行中；总时长；失败原因与建议
├─ 耗时构成：等首字 / 接收 / 工具 / 重试等待 / 压缩
└─ 时间线（按发生顺序，使用相对任务开始的时间）
   ├─ 模型请求（第 N 轮，第 M 次尝试）：等首字、接收、结果；可展开查看各网络阶段
   ├─ 工具调用：工具中文名、耗时、成功或失败
   ├─ 重试：原因、等待多久
   ├─ 上下文压缩：压缩前后 token
   └─ 期间的系统事件：断网、切后台、前台服务等

任务之外的系统事件（进程启动、服务回收等）单独成组
```

**规则：**
- **一件事只出现一次。** 底层的 `http.dns`、`http.tls`、`sse.*` 这类事件不单独展示，只作为模型请求的「阶段」出现在详情里。完整的原始事件只进入导出文件，不在界面上逐条罗列。
- **只展示有意义的字段。** 每类事件只显示与它相关的信息。例如网络变化显示网络类型；切前后台不再重复写「前台」；模型请求不附带网络、前后台这类环境字段，环境变化会作为独立的系统事件出现在时间线上。
- **时间与单位统一。** 任务内一律使用相对时间（+1.5 秒）；时长小于 1 秒用「毫秒」，大于等于 1 秒用「秒」保留一位小数；全页和导出用同一套。
- **所有面向用户的名称都用中文。** 事件、工具、阶段、错误都显示中文名。内部 ID（`get_current_context`、`openai_responses`）只在详情和导出里出现。
- **错误必须附建议。** 每类错误码对应「原因 + 建议」，例如 401 → 重新登录或检查 Key，429 → 稍后再试，断网 → 检查网络，后台断网 → 让 Movo 保持前台或允许后台运行。

## 5. 功能清单

| 功能 | 说明 | 优先级 |
|---|---|---|
| 任务列表 | 最新在前；每个任务显示结论、总时长、开始时间和简要构成 | P0 |
| 任务详情 | 结论与建议、耗时构成、时间线 | P0 |
| 请求详情 | 各网络阶段耗时、HTTP 状态、服务端请求 ID、接收大小、错误码、重试 | P0 |
| 进行中状态 | 当前步骤、已等待多久、多久没收到数据（回答 Q3） | P0 |
| 系统事件 | 发生在任务期间的放进该任务的时间线；任务之外的单独成组 | P0 |
| 筛选 | 全部 / 失败 / 进行中 | P0 |
| 导出 | 单个任务、全部；Markdown 文件或复制；包含设备型号、系统、App 版本 | P0 |
| 从对话直达 | 对话里失败或卡住的任务可以一键打开它的日志，不需要先去设置里找 | P1 |
| 搜索 | 按任务号、错误码、工具名搜索 | P1 |
| 原始事件 | 只在导出中提供，界面不展示 | — |

## 6. 边界（明确不做）

- 不记录对话内容、模型回答、工具参数和结果、API Key 或令牌。这和现在的隐私约束一致。
- 不做通用的 logcat 查看器，不采集其他 App 的日志。
- 不自动上传，导出由用户主动触发。

## 8. 验收标准

以真机上的真实场景逐条验证（只用小米测试机）：

1. 制造一次 401（令牌失效或 Key 错误）：日志能说出原因和建议，并定位到第几轮的哪次请求。
2. 制造一次断网：时间线上能看到断网发生的时间点，以及紧随其后失败的请求。
3. 一次慢任务：耗时构成能指出最慢的部分，并且各部分之和接近总时长。
4. 任务进行中打开日志：能看到当前步骤、已等待时长、距上次收到数据的时长。
5. 进程重启后（如果 D1 选 B）：之前的任务仍然可以查看。
6. 导出文件交给没看过界面的人，他能回答 Q1–Q4，文件里没有对话内容和凭据。

出 UI 时补充的细则（评审时一并确认）：
- 「卡住」的判定：任务进行中且 30 秒没有收到数据；此时对话里的执行卡片副标题变为「已 N 秒没有收到数据 · 查看日志」。
