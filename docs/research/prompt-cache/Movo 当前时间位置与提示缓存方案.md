# Movo「当前时间」位置与提示缓存方案（第 2 版，待 review）

日期：2026-10-06。状态：方案，还没改代码；第 6 节的事你定了再动手。
实测脚本和原始数据：`.docs/prompt-cache/`。Codex / Claude Code 调研：`.docs/prompt-cache/codex-claude-code-research.md`。

**第 2 版改了什么**
- 时间消息从「每次临时插一次、不存历史」改成「存进历史、之后原样重放」，和 Codex、Claude Code 的做法一致；
- 补了「上一次任务调过工具」的实测。第 1 版只测了纯问答，96% 在调过工具的对话里不成立；
- 查清两次任务之间 Movo 还会改写哪些历史，新增第 2 步：把上一次任务的模型输出原样存下来。

## 0. 一页看懂

**问题。** 每次任务，系统提示末尾都带一句「当前时间：2026-10-06 星期二 12:34」，精确到分钟，所以每次都不一样。提示缓存只认「从头开始一模一样的部分」，而工具定义（约 7000 token）和全部对话历史都排在这句后面，所以每次新任务都要从这里往后重新算。同一次任务里的多步调用不受影响，照常命中。

**第 1 版的漏洞。** 第 1 版只在「这次这句话」前面临时插一条时间，不存历史。下一次任务时，上一条时间消息就没了，它后面上一次任务的整个工具循环（调用、观察结果、回答）每次都要重算。纯问答时损失很小，所以测出 96%；上一次任务调过工具时只有 73%（3.2）。

**还有一处断点。** Movo 存历史时会丢掉模型的原始输出（思考、调用的编号等），下次重建成另一种格式发出去。所以即使时间放对了，缓存也会断在上一次任务的第一次模型输出那里（1.5）。

**本版改法，两步：**
1. **时间消息存进历史。** 每次任务开始时生成一条「环境信息」，放在你这句话前面，和这句话一起存进对话历史。之后每次请求都原样带上，不改、不删、不挪。系统提示里不再有时间。
2. **上一次任务的模型输出原样存**（第 6 节第 1 项要你定）。服务商和模型都没变时，下次请求原样回放；变了就照现在重建。

**效果（默认模型实测）。**

| 情况 | 现在 | 只做第 1 步 | 两步都做 |
|---|---|---|---|
| 上一次任务调过工具（真模型跑 6 步，约 2.8 万 token），下一次任务命中 | **9%** | 43% | **95%** |
| 只有问答的对话，下一次任务命中 | 20% | 96% | 96% |
| 约 4 万 token 的长对话，模型耗时 | 3.0 秒（不命中） | — | 2.4 秒（命中） |
| 问时间、算日期、不该提时间时不提（8 个场景各 10 次） | 77/80 答对，3 次去调工具查时间 | 80/80 | 80/80 |

**你会感觉到的变化。** 长对话、尤其是让它操作过手机之后，再问下一件事，每次快大约半秒。按量计费的服务商上，输入费用大幅下降（缓存的输入通常有大幅折扣，比例看服务商）。回答内容不变。

## 1. 现状（代码核实）

1. **时间在哪。** `AgentPromptBuilder.environmentLine()` 生成「当前时间：日期 星期 时:分（时区）」，每次任务算一次，作为最后一条系统消息（`AgentPromptBuilder.kt:169-178`，`AgentModelClient.kt:116`）。
2. **系统消息怎么进请求。**
   - Responses 接口：所有 system / developer 消息都拼进 `instructions`（`OpenAiRequestMessages.kt:28-44`），`input` 里跳过这两种角色（`ResponsesRequestBuilder.kt:54`）；
   - Chat Completions：system 合并成开头一条；developer 原样留在原位（`OpenAiRequestMessages.kt:8-16`）；
   - Anthropic：system 合并进 `system` 字段，developer 直接丢掉（`AnthropicMessagesProvider.kt:95-132`）。
3. **工具定义排在 `instructions` 之后。** `instructions` 一变，后面全部不命中（`.docs/voice-brevity/eval/cache_probe.jsonl` E0）。工具顺序是固定的（`ToolRegistry.kt:11`）。
4. **为什么当初放在系统消息里**（`.docs/full-review-1005/findings.md`）：
   - D1：时间最早加在用户消息开头，模型当成你新说的话，主动报时，还跑了 5 步无关工具；
   - T1-E1：放进系统消息后，模型偶尔把时间写进你让创建的文件，于是加了「它不是任务内容」这句。

   本方案不碰用户消息，时间是一条单独、写明来源的开发者消息，行为实测见 4.2。
5. **两次任务之间，历史不是原样重放。** 这是第 1 版没发现的。一次任务内，模型的原始输出原样回放，缓存没问题；任务结束存历史时会改写下面这些，下一次任务的请求从改写处开始就和上次不一样了：

   | 改写 | 在哪 | 缓存断在哪 | 本方案 |
   |---|---|---|---|
   | Responses 原始输出项（思考、调用编号和状态、回答的分段结构）丢掉，重建成「助手文本 + 精简调用」 | `ResponsesEphemeralState.kt:6`，`ResponsesRequestBuilder.kt:65-87`，测试 `AgentConversationCodecTest.kt:113-130` | 上一次任务的第一次模型输出 | 第 2 步改 |
   | 敏感工具（读文件、读设置、记忆、MCP 等）的参数和结果脱敏 | `AgentConversationCodec.kt:190-232`，`AgentSensitiveToolPolicy.kt:8-16` | 上一次任务的第一次敏感调用 | 隐私优先，不改 |
   | 你发的图片换成占位文字 | `AgentConversationCodec.kt:263-278` | 那张图 | 不改（图片不存是既定做法） |
   | 系统提示里会变的东西：记忆写入、装技能、工具开关、权限、语音和文字切换、换模型 | `AgentPromptBuilder.kt:49-183`，`AgentRuntimeRunExecutor.kt:101-191` | 整段 | 少见，不处理 |
   | 上下文压缩（快满时） | `AgentContextCompactor.kt:73-88` | 整段 | 偶尔，不处理 |

6. **各路径的缓存现状。**
   - ChatGPT 订阅：设了 `prompt_cache_key`，值是对话 id，跨任务稳定（`ChatGptCodexRequest.kt:36-46`），但同样断在时间和输出重建上；
   - 默认模型（方舟）和内置 OpenAI 走 Responses，靠服务商自动前缀缓存；
   - Anthropic 没设 `cache_control`，现在完全没有提示缓存（第 8 节）。

## 2. 调研：Codex 和 Claude Code 怎么做

详见调研文档，结论：

| | Codex | Claude Code | 本方案 |
|---|---|---|---|
| 系统提示里放时间 | 不放 | 不放。官方博客把「静态系统提示里放精细时间戳」列为自己踩过的坑 | 不放 |
| 动态信息怎么给 | 作为消息追加到对话里 | `<system-reminder>`，附在下一条消息里 | 作为消息放在你这句话前 |
| 发出后会不会再改 | 写进历史，原样重放，不改写 | 写进历史，原样重放；「重新渲染导致缓存不命中」被当成 bug 修过多次 | 写进历史，原样重放 |
| 时间粒度 | 默认只给日期 + 时区，变了才追加；按秒的时间提醒是实验功能，也写进历史 | 只给日期，跨天时追加一条说明 | 到分钟，每次任务一条（3.3） |
| 模型原始输出 | 原样存进历史（含加密思考），下次原样发 | 原样记录、原样重放 | 第 2 步：服务商和模型没变时原样发 |

## 3. 方案

### 3.1 第 1 步：时间消息存进历史

**生成。** App 发起一次任务时（`AgentAppState.launchConversationRun`）生成一条时间消息：
- 角色 developer，编号 `env-<runId>`；
- 放在你这句话前面，和这句话一起存进对话历史。

之后每次请求都原样带上，不改、不删、不挪。同一次任务里的多步循环不更新时间。

**文字。** 在现在那句的基础上，开头说明来源和时效：

> 环境信息（Movo 在这次任务开始时自动提供，不是用户说的话；对话里更早的时间都已过时，以这条为准）：当前时间：2026-10-06 星期二 12:34（Asia/Hong_Kong，UTC+08:00）。只在任务需要时使用，例如换算今天、明天、几小时后；不要主动报时，也不要因为它去做用户没要求的事。它不是任务内容：用户没要求时，不要把时间写进文件、消息或回答。

「以这条为准」是这一版加的。历史里会留着一串旧时间，实测加不加都对（4.2），留着更稳。

**哪些任务带。**
- 带：App 里的每一轮，包括监听叫醒的一轮、语音对话的一轮、补充后续跑的一轮；
- 不带：回答重写、上下文压缩这类内部请求；
- 外部入口（小爱接力等）没有 App 对话历史，保持现在的做法（时间在系统提示里）。

**请求怎么组装。**

| 路径 | 改后 |
|---|---|
| Responses（默认模型、内置 OpenAI、ChatGPT 订阅） | 历史里的时间消息作为 `input` 里的 developer 消息原样发；`instructions` 里不再有时间。要区分「开头的系统段」和「历史里的时间消息」：现在 developer 一律并进 `instructions`（`OpenAiRequestMessages.kt:44`），要改 |
| Chat Completions、Anthropic | 保持现在的做法：时间仍在系统提示里，历史里的时间消息跳过不发（第 6 节第 2 项） |

**其他地方跟着处理。**

| 场景 | 处理 |
|---|---|
| 上下文压缩 | 时间消息和它后面那句话算一组，一起保留或一起进摘要；这次任务的那条一定保留。现在压缩只特殊对待 user 和 tool（`AgentContextCompactor.kt:150-160`），要补 |
| 编辑重发、重新生成 | 那句话前面的旧时间消息一起去掉，按重发时刻生成新的。编辑按「倒数第几条 user」对位（`AgentConversationRevisionReducer.kt:76-82`），时间消息不是 user，不影响对位 |
| 事件轮撤回（没真正开始就让路） | 它的时间消息一起撤掉 |
| 对话列表、导出、记忆 | 不显示时间消息 |
| 轮次计数 | 只数 user，不受影响（`AgentContextSession.kt:24-27`） |

### 3.2 第 2 步：上一次任务的模型输出原样存（第 6 节第 1 项）

**现在为什么不存。** 代码注释写着「仅在单次 Agent run 内传递，稳定会话 codec 不认识并会主动丢弃」，测试也专门断言加密思考不进存档。当初的考虑是不把服务商私有的输出（比如 ChatGPT 的加密思考）写进稳定存档。

**改法。**
- Responses 的原始输出项随助手消息一起存，并记下来自哪个服务商、哪个模型；
- 下次请求时服务商和模型都没变，就原样回放（和一次任务内现在的做法一样）；变了，照现在的方式重建；
- 敏感工具的脱敏、图片占位不变：这两处缓存照断，隐私优先；
- 上下文压缩照现在的做法丢掉原始输出项。

**代价。**
- 存储变大：思考内容的文字现在已经存了，新增的主要是编号、状态和结构；ChatGPT 的加密思考每段几 KB；
- 换服务商或模型后的第一次任务退回重建，本来也不命中；
- 存档格式加字段，旧数据没有这个字段就照现在重建，兼容。

**收益。** 上一次任务调过工具时，下一次任务的命中从 43% 到 95%（4.1）。Movo 的任务大多要操作手机，这一步的收益比第 1 步还大。

### 3.3 不做的事

| 做法 | 为什么不做 |
|---|---|
| 时间只给到日期（Codex、Claude Code 的默认），精确时间让模型自己查 | Movo 没有专门读当前时间的工具，只能调终端 `date`，问「几点了」要多一轮，语音轮更慢；「半小时后提醒我」这类相对时间也离不开分钟。每次任务一条分钟级消息存进历史只多约 100 token，不影响缓存 |
| 同一次任务里每一步都追加新时间（Codex 的实验功能） | Movo 的任务大多几十秒内结束；监听叫醒的每一轮本身就是新任务，会带新时间 |
| 只在本次临时插一次、不存历史（第 1 版） | 上一次任务的工具循环每次重算，调过工具时只有 73% |
| Chat Completions 和 Anthropic 一起改 | 这次不做（第 6 节第 2 项） |

### 3.4 和语音简短回复的关系

语音段仍是 `instructions` 的最后一条，不受影响。时间挪走后，语音轮和文字轮的 `instructions` 都不再含时间：
- 语音轮和语音轮之间整段命中；
- 文字轮和语音轮之间仍断在 GFM 段，和语音方案 2.4 的分析一致。

## 4. 实测

条件：打包默认模型（方舟 Agent Plan，Responses），真实系统提示和 36 个工具，各 3 次取中位。

### 4.1 缓存

**真实多步任务**（`cache_env3.py` → `cache_env3.json`）。对话里先有两轮问答；任务 N 是「打开设置，搜索蓝牙」，用真模型跑完（6 步，模型的原始输出项在任务内原样回放，和 Movo 一致）；然后看任务 N+1「再看一下 Wi-Fi」第一次请求命中多少，时间比上次晚 6 分钟。

| 放法 | 输入 token | 命中 | 中位命中率 |
|---|---|---|---|
| 现在（时间在 `instructions` 末尾，历史按现状重建） | 27905–31810 | 2432 | **9%** |
| 第 1 步（时间消息存进历史，历史按现状重建） | 27980–31974 | 11904 | **43%**，断在任务 N 的第一次模型输出 |
| 两步都做（时间消息存进历史，模型输出原样存） | 24968–28948 | 24320–24832 | **95%** |

**模拟工具结果**（`cache_env2.py`，任务 N 的 3 次调用和结果手写，前后两次逐字一致，用来单独比较时间的放法）：

| 放法 | 输入 token | 命中 | 中位命中率 |
|---|---|---|---|
| 现在 | 16090 | 2048–2432 | 15% |
| 第 1 版（临时插一次，不存历史） | 16091 | 11776 | 73% |
| 本版（存进历史） | 16184 | 16000 | 99% |

**纯问答**（第 1 版的 `cache_env.py`）：现在 20%，第 1 版和存进历史都是 96%。

### 4.2 行为（`env_eval2.py` → `env_eval2.jsonl`，每种放法每个场景 10 次）

历史里的旧时间消息是之前任务开始时的时间（08:00、09:30），现在是 12:34。「答对」算 86 或 87 天（算不算今天，口径不同，都对），去调工具查时间单独记。

| 场景 | 现在 | 存进历史（原措辞） | **存进历史（新措辞）** |
|---|---|---|---|
| 「现在几点了」答 12:34 | 10/10 | 10/10 | 10/10 |
| 「距离元旦还有几天」 | 10/10 | 9/10，1 次调终端 | 10/10 |
| 「明天是星期几」答星期三 | 10/10 | 10/10 | 10/10 |
| 「介绍一下火星」不提时间 | 10/10 | 10/10 | 10/10 |
| 「新建 note.txt，内容写：买牛奶」文件不带时间（T1-E1） | 10/10 | 10/10 | 10/10 |
| 有历史时「看一下系统版本」只调相关工具（D1） | 10/10 | 10/10 | 10/10 |
| 上次答过 08:00，再问「那现在几点」答 12:34 | 8/10，2 次调工具 | 10/10 | 10/10 |
| 历史里有两个旧时间后算元旦 | 9/10，1 次调终端 | 10/10 | 10/10 |

第 1 版记的「存进历史时元旦题 7/10」复查过：是按 87 判、86 算错，再加上 2 次去调终端；没有一次用错时间。

### 4.3 速度（`latency_long.json`，各 4 次）

约 4 万 token 的对话历史、一句话回答：命中 2.4 秒，不命中 3.0 秒。约 1.1 万 token 时差别在 0.2 秒内（语音方案 2.4）。对话越长，收益越明显。

## 5. 风险

| 风险 | 处理 |
|---|---|
| 模型把时间当成你说的话（D1） | 不进用户消息，单独一条开发者消息，写明来源。4.2 无主动报时、无乱调工具 |
| 模型把时间写进文件（T1-E1） | 「它不是任务内容」保留。4.2 写文件 10/10 干净 |
| 历史里一串旧时间，模型用错 | 新措辞写明「更早的时间都已过时」。4.2 两个旧时间后算日期 10/10 |
| 时间消息被重新生成、挪动，缓存又断 | 生成一次，存进历史后不再改。加单测：连续两次任务，后一次请求的前缀和前一次逐字一致（第 7 节） |
| 原样回放的模型输出发给了别的模型 | 存的时候记下服务商和模型，不一致就重建 |
| 压缩把这次任务的时间丢了 | 时间消息和这句话算一组，这次任务的那组一定保留；万一请求里找不到，退回把时间放进 `instructions` |
| 方舟对 developer 角色、缓存规则的细节 | 已实测：接口接受、能命中（4.1）。最小长度、过期时间没有查文档 |

## 6. 要你定的事

1. **第 2 步（模型输出原样存）做不做。**
   - A）两步一起做（推荐）：调过工具的对话 9% → 95%；
   - B）先只做第 1 步：9% → 43%，第 2 步以后再说。

   第 2 步改了存档格式，需要你认可「Responses 的原始输出（含思考、ChatGPT 的加密思考）存进本机对话存档」。
2. **范围。**
   - A）只改 Responses 这条路（默认模型、内置 OpenAI、ChatGPT 订阅），Chat Completions 和 Anthropic 保持现状（推荐）；
   - B）Chat Completions 也改成对话中间放消息。

   B 要逐个服务商实测兼容性，目前手上只有默认模型的 Key。

## 7. 怎么验证

**1. 单测**
- 连续两次任务的前缀一致：用 `AgentModelClientLoopTest` 里的 `ScriptedProvider` 跑两次 `complete()`，第一次的 transcript 当第二次的 history，两次请求都过 `ResponsesRequestBuilder.build`，断言第二次的 `input` 以第一次最后一个请求的 `input` 开头（模型输出项用 `ResponsesEphemeralState.attachOutputItems` 模拟）。现在没有这种测试。
- `instructions` 不含时间；时间消息在这次的用户消息前，后续步骤位置不变。
- Chat Completions、Anthropic 的请求和现在逐字一致。
- 压缩、编辑重发、事件轮撤回后时间消息的去留。
- 第 2 步：换模型后退回重建；旧存档没有原始输出项时照现在重建。

**2. 实测回归**
- 用改后的真实请求跑 `cache_env3.py`：调过工具的跨任务命中，两步都做 ≥ 90%，只做第 1 步 ≥ 40%；
- 跑 `env_eval2.py`：8 个场景与现在持平或更好。

**3. 真机**

小米云真机上（独占设备，见 Dora 隔离要求）：
- 同一对话里「打开设置搜索蓝牙」→「再看一下 Wi-Fi」→「现在几点」，从运行日志里的 `usage_received … cache=` 看每次任务第一次请求的缓存数；

## 8. 单独提出的问题（不在本次范围）

1. **Anthropic 路径完全没有提示缓存**：没设 `cache_control`。要开的话，在工具定义和系统提示末尾打缓存断点；时间也要挪进对话，但 Anthropic 不允许对话中间的 system 消息，只能像 Claude Code 那样放进用户消息里一段单独、冻结的提醒，这正是当初出 D1 的位置，需要用 Claude 的 Key 单独实测。
2. **内置 OpenAI 的 Responses 路径没设 `prompt_cache_key`**。OpenAI 建议设一个稳定值帮助路由，可以和 ChatGPT 订阅一样用对话 id。默认模型（方舟）支不支持这个参数没有查。
3. **上下文压缩、推荐追问这类内部请求用的是随机 key**（`AgentProvider.kt:47`，`AgentContextCompactor.kt:106`），每次都不命中，可以顺手改成对话 id。
