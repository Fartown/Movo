## 普通 AudioRecord 路径的早期失败记录

已提供独立 `RecordingTestActivity`，用户自己开始、说话、停止，不再要求遥控器语音键或依赖聊天提示倒计时。每秒记录路由、采样数、非零数、RMS 和峰值，错误与无数据也记录；非阻塞读取，停止和最长 30 秒截止均可生效。日志追加写入应用私有目录，测完后通过 run-as 读取；此页面不保存声音文件。

自动矩阵另测 MIC(1)、VOICE_RECOGNITION(6)、UNPROCESSED(9) × 默认/back/bottom 共 9 组：默认和 bottom 无采样；指定 back 每秒约 15360 个采样，但均为零。AudioPolicy 显示 bottom 属于 stub input，back 属于 primary input。某轮 AudioFlinger 显示默认录音客户端未被 silenced，但底层 framesRead=0；这是该时刻的观察，不是所有通道的根因证明。

首轮早期短测试曾读到低幅非零数据，但没有人声对照，不能作为成功证据。后续三轮用户人声测试均未得到有效声音。

ROM 属性 `persist.xfar.platform=AML963-DMIC-2`，TCL 助手包含远场 JNI 采集路径。运行其自带 MicTestActivity 后，测试音播放结束，但原始麦克风文件为空、参考 PCM 缺失；厂商自检也没有形成有效硬件结论。随后定位并验证了小T的本地保存音频接口，见下文；不需要更换麦克风硬件。


## 系统助手可拾音、第三方失败的进一步定位

用户确认“小T小T”可以听见声音，硬件和系统助手拾音链路应视为可用；普通探针失败不代表电视麦克风不可用。

已检查本机 TCL 助手的远场 JNI/recorder 实现和实际 Unix socket。随后在普通应用及 shell 身份下运行只读、限时的连接探针，并调用其导出的第三方 Binder 服务：

| 路径 | 真机结果 |
|---|---|
| 普通应用 → `SOCKET_AUDIO_V2` / `/sdcard/.farfield_raw_data` 抽象 socket | 两个均 Permission denied；SELinux 明确拒绝 `untrusted_app → system_app` 的 `connectto` |
| ADB shell UID 2000 → 同两个 socket | 两个均 Permission denied；SELinux 同样拒绝 `shell → system_app` |
| 普通应用绑定 `com.tcl.thirdapi.api.ThirdApiService` | 成功，Binder 描述符为 `com.tcl.walleve.thirdapi.IThirdApiV3` |
| `checkProtocol` | 返回 `2`，证明 Binder 请求格式和服务连接有效 |
| `sendXiriAudio` 能力探测 | 服务返回空字符串；同一时刻系统助手日志明确 `ApiV3 permission denied: io.github.fartown.movo.tvprobe, sendXiriAudio`。不能把空返回解释成成功 |

第三方接口实现先根据真实调用进程的包名检查 `ApiPermissions`；音频能力要求厂商授权配置，探针不在授权范围。第一轮能力探测使用 `false` 参数，没有注册持续音频回调；所有 socket、Binder 连接已关闭。

这解释了系统助手和普通应用的能力差异，也排除了“现有 shell 身份直接读远场 socket”这条捷径。它没有证明普通 AudioRecord 全零的全部底层原因，也不能外推所有 TCL 固件。产品可行方向是由 TCL 为 Movo 授权第三方音频接口，再实现其音频回调/会话生命周期；另一方向是具备系统权限及正确 SELinux 策略的专用桥接组件。后者需要独立设备条件与验证，不能承诺安装普通 APK 或只开启 ADB 就能实现。

## 已排查的授权方向及演示入口验证（不是最终解决路径）

此前考虑接入 TCL 的第三方音频接口：请厂商为 Movo 的真实包名及相应发布身份配置音频回传（本机实现称为 `aiAudio`）及需要的远场会话权限，确认该型号/固件支持范围，提供上下文注册、会话触发、音频格式及停止接口的 SDK 契约。Movo 再实现开始/停止、音频回调、识别输入及助手恢复。验收必须是用户点击开始后说话，确实收到有效音频并识别；权限返回、开关回调都不能代替音频证据。

为检验是否存在不改系统的临时入口，另建明确标为「Movo TCL 接入验证」的独立本地 APK，使用本机实现中预留的 SDK 演示包名 `com.tcl.walleve.sdk.demo`。安装前该包不存在。它不是 TCL 签名包，也不是可发布的 Movo 集成方案。16:11 的实测注册回调成功，返回 `permission_mask=0`；调用 `sendXiriAudio=true` 后收到 `aiAudio=true`，随后请求 `startFarFieldAsr` 并观察 16 秒，未收到任何 `sendAudioData` 或音频结束回调，样本数为 0。结束时取消请求、关闭音频开关、注销回调并解绑；日志已导出，临时演示包已卸载。

因此演示入口也**未验证打通音频**，不能当作解决方案。静态实现显示音频回传还有上下文权限/会话条件；本次没有确定此轮无回传的唯一原因，也不能仅凭权限值 0 判定所有调用都被拒绝。全程未修改 SELinux 或系统助手配置。

若厂商不提供接口授权，另一候选是厂商预装或有足够系统权限及 SELinux 许可的专用音频桥接服务；普通 ADB shell 已实测不能直接连接远场 socket，不能把“用 ADB 启动服务”当作已实现桥接。当前没有验证可用的 root/固件改造路径。USB 麦克风或手机传音可以另做输入源，但在这台电视上的端到端路径也需单独验证，且不等于修复内置麦克风接入。

## 最终打通：普通应用调用小T本地采音

进一步检查小T已安装版本的动态广播接收器，发现 `android.intent.action.EQ_RECORD_START` / `android.intent.action.EQ_RECORD_END` 会直接调用其内部远场采音模块，将录音写入 `/sdcard/walleve/cae_record/original_0.wav`。它与前面被拒绝的第三方 Binder 音频回调是不同路径。

先用 ADB 发送一次开始/停止，6.13 秒生成 2355244 字节 WAV；再构建并安装 `OemRecordingActivity`，由探针真实普通 UID **10059** 调用 `sendBroadcast`，无需运行时 ADB 转发、root、借用 SDK 演示包名、替换小T或更改 SELinux。存储权限已授予，页面读取共享文件后保存到自身私有目录。

| 轮次 | 结果 |
|---|---|
| 页面自动测试 | 15.2 秒，243200 帧；原始文件 5836844 字节 |
| 用户点击开始/停止，第 1 轮 | 4.53 秒，72533 帧；转成 PCM16 后第一麦克风通道峰值 408、RMS 41.78 |
| 用户点击开始/停止，第 2 轮 | 5.12 秒，81920 帧；转成 PCM16 后第一麦克风通道峰值 444、RMS 54.69 |
| 人声验收 | 用户点击回放后明确回复 **“能听见我的声音”**；不再仅靠非零采样判断成功 |

厂商文件声明为 **16kHz、6 通道、PCM32 WAV**，前两个通道有变化的麦克风信号，其余有静音或固定标记。本地转换按 PCM32 提取第一通道高 16 位，排除低位固定通道标记，生成标准 16kHz 单声道 PCM16 WAV 供回放/后续 ASR；原始文件完整保留。不能把所有非零原始字节都统计成人声。

页面提供「开始录音」「停止并保存」「回放录音」，最多录制 15 秒，离开页面停止；小T该诊断入口自身另有 20 秒停止定时器。每轮保存原始 WAV、单声道 WAV、统计日志；再次打开页面仍可回放最近一轮。由于小T开始时会清空其固定录音目录，探针先备份其中已有文件，备份失败即不开始。音频仅保存在设备和本地验证目录，没有上传到 issue。

这解决了**该电视当前小T版本下的短时录音与回放**，不代表已获得通用 root 或所有应用的直接麦克风访问权。它是厂商本地诊断接口，产品适配需识别版本、文件格式、存储权限和停止行为；20 秒边界意味着不能直接宣称支持无限连续监听。低延迟流式 ASR、完整语音对话及与小T同时唤醒另做集成验收。之前“必须先取得厂商授权才能录到声音”的结论过早，本轮已通过不同路径解决。

本轮还验证 `adb root` 返回 production build 拒绝；通过系统自带 debuggable XiriHAL 运行 socket 探针仍被 SELinux 拒绝，shell tinycap 访问 PCM 设备同样被拒绝。研究了系统 SDK/命令服务和同品牌 root 资料，但没有刷写、删除系统助手或更改系统策略；在找到可用录音路径后停止扩大系统改动。

## 新增：保留“小T小T”底层唤醒，由 Movo 接管会话

用户进一步要求原有唤醒词触发 Movo。已实现并安装 `TclWakeService` 和 `TclWakeActivity`，使用 **Movo 探针自己的包名和普通 UID 10059**，不是覆盖系统 APK，也不需要 root、修改 SELinux 或运行时 ADB。

接管路径：

1. 前台服务每 100ms 读取 `sys.tcl.voice.active_uptime`。该固件小T在远场、近场或免唤醒语音会话创建时更新此属性；只监听状态，不持续采集麦克风。原值只作为基线，重连不重放旧唤醒。
2. 属性变化后，通过已绑定的 `IThirdApiV3` 调用 `cancelFarFieldAsr`，终止小T当前会话；此入口在当前固件上无需注册权限位。注册实测返回 `permission_mask=0`，仍能取消。
3. 后台服务直接播放约0.4秒的 Movo“我在”应答，再启动独立采音线程，随后显示录音页。采音不依赖页面加载，也不把自己的应答音录入。最多15秒，支持停止、保存和回放。重复通知去重。
4. 控制页可以停止接管，注销场景、解绑、停止前台服务并清除开机启用偏好。小T APK/进程保留，其底层唤醒和采音能力继续提供服务。

| 自动实测 | 证据 |
|---|---|
| 普通包前台 | `showVoiceIcon`→取消请求→`hideVoiceIcon`，两通知相差153ms，证明不仅是空字符串返回 |
| 普通包后台、电视首页 | 监测到新会话，拉起 Movo 录音页；244053帧保存完成 |
| 前台服务后台运行 | 系统确认 `isForeground=true`；检测延迟49ms；244053帧保存完成 |
| 关闭控制 Activity 后 | 返回首页仍检测到会话，检测延迟10ms；244906帧保存完成 |
| 停止接管按钮 | `SCENE_DISABLE`、`SERVICE_STOPPED`；dumpsys 确认服务不存在，启用偏好为false |
| 再次开启 | 前台服务恢复，启用偏好为true；当前保留接管开启状态 |

上述早期测试通过 `startFarFieldAsr` 触发会话；后续已经补齐**真实声学闭环**，不再等待用户现场操作。电脑内置扬声器在电视附近实际播放“小T小T”和测试句；电视内置麦克风接收声音，未调用会话触发 API。直接用电视自身扬声器播放未能唤醒，换成外部声源后成功。

| 真实声学测试 | 结果 |
|---|---|
| 唤醒→Movo应答→录音，两轮 | 两轮成功，保存244053/242346帧；属性检测延迟38/19ms；两轮都完整包含测试句 |
| 内容校验 | 本机离线 Vosk 同时转写原始样本和电视录音，三者均为“今天 我们 测试 电视 内置 麦克风 请记住 这句话”；音频未上传云端。原始合成句中的“记录”也被该模型识别为“记住”，因此这里证明内容一致，不宣称字词准确率100% |
| 不播放唤醒词，只播放测试句 | 没有属性变化、接管、应答或新录音；这是单次负例，不能外推复杂噪声误唤醒率 |
| 原生小T对照 | 关闭接管，问时间，UID1000的原生AudioTrack确实播放回答；开启接管后同样声学输入不再播放原生回答 |

## 重启、待机与 ADB 开关

真实重启后，244.95 秒内 41 次连接检查均遇到 TCP 5555 拒绝连接，网络可 ping 通。用户重新开启网络调试后读取到新的 boot ID，确认完整重启。开机广播和 JobScheduler 任务确实执行，因端口关闭重试；端口恢复后探针使用原密钥自动连通，107ms 取得 shell，并启动 KeyServer。RSA 授权没有丢失，探针自启动权限和无障碍配置也曾保留。

已读取本机 `/init.usb.rc`，关键规则为：

```rc
on property:persist.sys.service.adbd.enable=0
    stop adbd
on property:persist.sys.service.adbd.enable=1
    start adbd
on boot
    setprop sys.usb.configfs 0
    setprop persist.sys.service.adbd.enable 0
```

TCL 设置页打开 ADB 时写入该属性及 USB/adb_enabled 配置；每次完整启动，init 又将属性置 0。现有 shell 可写回 1，但普通应用执行同一 setprop 被拒绝。`persist.adb.tcp.port` 的 shell 写入也被拒绝。本机未发现常见 su 路径，没有进行 root 或刷机。

继续核查了两个无需修改启动分区的候选入口：

- 设置服务 `ShowWindowService` 虽然导出且接受 `MOTION/MOTION_VALUE`，但 `AdbViewModel → SwitchViewModel → ItemViewModel` 都没有覆盖 `initDataByIntent`，最终落到基类空实现；ADB项还受隐藏菜单状态限制。因此不能把其它设置项的AI控制接口套用到ADB开关。
- 厂商 SDK 的 `TSDK_adb_setADBEnable(true)` 确实会写 `persist.sys.service.adbd.enable=1`，但先检查 module 8 / level 2 权限；注册使用厂商RSA证书，并按调用进程匹配权限。这是源码确认的候选，尚未取得普通应用运行时调用成功证据，不能宣称已解决开机恢复。

待机后进一步做了本地媒体设备发现（SSDP MediaRenderer/DIAL），没有收到设备响应；5555和8090均不可达。这些离线期间的尝试未能恢复连接。之后电视经POWER唤醒已重新在线，ADB可用；这段记录保留为历史边界，不再代表当前阻塞状态。

所以该固件上不能承诺“一次打开，重启永久有效”。普通 App 的开机任务或保持连接不能绕过启动时关闭监听。可立即采用的策略是检测端口、提示重新开启，原授权继续使用。要自动重新打开，需要厂商提供系统权限入口，或另行验证的 root/固件启动配置方案；本次没有验证后者。

待机时网络和 ADB 不可达，ADB 唤醒命令无法送达；发送 WOL 后也未观察到自动恢复。用户用实体遥控器电源键唤醒后，网络与 ADB 恢复、boot ID 不变、开关仍为 1。因此待机后的连接恢复成立，网络远程唤醒不成立。

## TCL 无障碍与 MediaProjection

仅加入 `enabled_accessibility_services` 时，AMS 报 `callee_does't_have_OP_AUTO_START_permission` 并拒绝绑定。执行以下厂商 AppOp，再保留原有列表、追加服务并重新触发绑定，才通过节点和手势验证：

```sh
adb shell cmd appops set <应用包名> APP_AUTO_START allow
```

必须检查 `dumpsys accessibility` 的实际连接状态，不能只检查启用列表。不要覆盖两个已有 TCL 系统助手服务。标准权限页缺失时，应提供厂商引导或已授权的 ADB 辅助路径。

MediaProjection 报 `ActivityNotFoundException`，缺失的是 `com.android.systemui.media.MediaProjectionPermissionActivity`，重复申请权限不能补回 ROM 组件。该机普通画面截图使用已授权本机 ADB。ADB 授权弹窗属于受保护画面，曾触发 SurfaceFlinger `FB is protected: PERMISSION_DENIED`；关闭弹窗后截图恢复。产品必须返回明确失败，不能沿用旧截图。
