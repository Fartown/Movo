## 0. 一页看懂

### 一句话

语音轮的回答在两个环节各加一道处理：
- **模型写回答时**：通过系统提示告诉它会被念出来，按语音规则写短；
- **念出来之前**：用固定规则去掉残留符号。

另外有两处不靠模型自觉、直接在程序里改的：
- 语音轮不给模型「弹卡片提问」这个工具；
- 超级小爱入口也算语音轮。

### 你会遇到什么

| 你说 | Movo 会怎么回答 |
|---|---|
| 普通问题（「为什么天是蓝的」） | 一两句完整的短句，大约 60 字以内 |
| 让它做事（「明早七点叫我起床」） | 一句结果：「好了，明天早上 7 点的闹钟已经设好。」 |
| 事没做成、只做了一半、做了但没确认 | 直接说是哪种情况、为什么、你接下来能做什么，不说「好了」 |
| 查到很多条（「最近有快递通知吗」） | 说最相关的一到三条（取件码照念），其余可以在执行卡里看 |
| 明确要长（「详细讲讲黑洞」「念全文」） | 可以说长，用短句；「一步步教我」先说两三步，再问要不要接着说 |
| 缺关键信息（「帮我定个闹钟」） | 直接用一句话问「要定几点的？」，会被念出来，你接着说就行 |
| 回答里有网址、订单号、文件路径 | 不念 |
| 电话、验证码、密码 | 只在你这句话明确要时才念 |
| 屏幕上 | 对话里显示的就是念的这段文字（第 7 节第 1 项） |

### 例子：「番茄炒蛋怎么做」

| | 现在 | 改后 |
|---|---|---|
| 模型写出 | 3 次分别 263、182、96 字，其中 2 次是「1. \*\*备料\*\*：…」这种编号列表加粗体 | 10 次在 42–101 字之间，中位 54 字，例如：「鸡蛋打散加少许盐，热油炒到刚凝固就盛出；番茄切块下锅炒出汁，倒回鸡蛋，加盐和一点糖翻匀出锅。想更详细我再说。」 |
| 念出来 | 原样照念，符号也念；按每秒约 4.5 字粗估，约 40 秒（豆包实际语速待真机测） | 约 12 秒 |
| 开口前要等多久 | 不变。模型生成耗时 2.5–3.1 秒，主要花在推理上，回答变短几乎不影响 | |

两列都是真实模型的原文。「改后」用的是第三轮实测的规则稿，和 2.3 的最终稿只差两处，见 2.3 末尾。

### 前提

「其余可以在执行卡里看」依赖刚做完的工具可视化（执行卡里每一步能点开看详情）。它现在还在 worktree `Movo-toolviz` 里没提交，要**先合入 main**，再做本方案。

## 1. 现状与问题（代码核实）

1. **模型怎么知道是语音轮。** 语音会话里说的话带着会话编号 `voiceSessionId` 发出，运行时据此设 `voiceConversation = true`（`AgentRuntimeRunExecutor.kt:239`），拼提示词时多加一条语音提示。详见第 4 节。
2. **现在的语音提示只有一句**（`AgentPromptBuilder.kt:167`）：「当前通过语音对话交流。未要求长答时尽量用一至三句自然口语回答…」。它排在中间，前面的核心规则里还有一段「最终答复使用 GitHub Flavored Markdown…可以用标题、列表或表格」，两条打架。
3. **追问卡片不会被念出来。** 模型缺信息时可能调 `ask_user` 弹卡片提问。语音模式下卡片上的问题不念（`VoiceConversationController.kt:131-145` 不处理交互事件），用户只会听到一片安静。实测：
   - 现在的提示下，「帮我定个闹钟」3 次里 2 次用了卡片；
   - 第三轮规则稿下，5 次里 1 次用了卡片。
4. **念的是正文原文**（`VoiceReplyContent.kt`），不去 Markdown。开了联网搜索时，App 还会往正文里插 `[[1]](网址)` 这种引用和末尾的「来源：」列表（`ResponsesCitationFormatter.kt:22-34`），提示词管不到这些，会被念出来。
5. **超级小爱入口**：用小爱 TTS 念 Movo 的回答，但发任务时不带语音标记（`XiaoAiHooks.kt:557-563`），提示词按文字轮走。它的结果显示在小爱卡片上，不进 Movo 的对话记录。
6. **要等整段生成完才开始念**，不是边生成边念。

## 2. 提示词设计

### 2.1 三个约束

| 约束 | 要求 |
|---|---|
| 指令遵循 | 语音规则要压得住前面的格式要求，也要压得住历史回答的示范；不能有互相打架的规则 |
| 对业务的影响 | 文字轮一个字不变；不改变模型查证、调工具、如实报告结果的行为 |
| 缓存 | 不额外破坏提示缓存，见 2.4 |

### 2.2 布局：选 A——语音轮删掉格式段，语音段放最后

共比较了三种布局，数据见 2.4、2.5 和附录 A：

| 布局 | 做法 | 指令遵循（带 Markdown 的次数） | 对文字轮的影响 | 缓存（文字轮之后第一个语音轮） |
|---|---|---|---|---|
| **A（推荐）** | 语音轮从核心规则里删掉 GFM 格式段；语音段放所有系统消息最后 | 1/94；最易出格式的场景 1/10 | 无 | 命中 0（其他情况和 B 一样） |
| B | 核心规则不动，只在最后加语音段 | 2/91；最易出格式的场景 2/10 | 无 | 命中约 2000 token |
| C | 把 GFM 段挪成单独一条靠后的消息，语音轮换成语音段 | 未单测，语音轮内容与 A 相同 | **有**：文字回答变长，例如「详细讲讲黑洞」1808 → 2171 字 | 命中约 2000 token |

「最易出格式的场景」指历史里已有一条长篇 Markdown 回答、再追问。

**选 A 的理由：**
- 它和 B 一样不动文字轮；
- 去掉了互相打架的规则，出格式的次数也略少；
- 缓存代价只发生在「从文字切到语音」的那一轮，约 2000 token，对速度的影响不到 0.2 秒，见 2.4。

C 为了缓存改动了文字模式现有的表现，不划算。

**A 和 B 在统计上没拉开差距。** 1/10 对 2/10，样本小。如果你更看重「核心规则一个字不动」，B 也可以接受，代价是多一点出格式的概率，由 3.2 的去格式兜底。

**消息顺序（语音轮）：**

| # | 改前 | 改后 |
|---|---|---|
| 1 | 核心规则（含 GFM 段） | 核心规则，**只删 GFM 段**（含紧跟的表格排版句）；「简单问题直接简短回答…」这句**保留**，它不冲突，也没测过删掉的效果 |
| 2–4 | 终端说明、浏览器说明、工具用法 | 不变 |
| 5 | 角色人设（角色会话才有） | 不变 |
| 6 | 语音一句话 | 删掉，挪到最后并扩写 |
| 7–9 | 记忆、技能、环境信息 | 不变 |
| 角色补充设定、深度提示（角色会话才有，`RoleplayRunContext.kt:52-65`） | 排在语音提示后面 | 不变，但语音段要排在它们**之后** |
| 末尾 | — | **语音段（2.3）** |

**角色会话：**
- 角色核心规则里也有一句 GFM 要求（`AgentPromptBuilder.kt:103`），语音轮同样删掉；
- 「角色交流的语言、语气、长短…以人物设定为准」这句，语音轮改成「语言、语气和叙事方式以人物设定为准」，长短交给语音段；
- 语音段末尾加一句「语气、称呼和人设照旧，只有格式和长短按这里」。

### 2.3 语音段原文（最终稿）

```
【语音模式】这一轮用户在用语音和你说话。你的最终答复会被念出来，屏幕上显示的也是同一段文字，用户可能没在看屏幕。下面的要求替代前面关于 Markdown 格式和回答长短的说明，前面对话里用过标题、列表或表格也一样；如实说明结果、证据和不确定性的要求照旧，用户这句话里的明确要求优先。
1. 像打电话一样说话：一般一到两句完整的短句，中文大约 60 字以内，其他语言同样一两句；先说结论或结果，不铺垫、不复述用户的话。不要为了变短把很多信息挤成一长串。
2. 只写能直接念的纯文字，不用 Markdown 和表情；数字、时间、金额照常用阿拉伯数字写。网址、文件路径、包名、订单号不念；取件码、时间、金额照常说；电话号码、验证码、密码只在用户这句话明确要时才说。
3. 做完操作用一句话说结果，例如「好了，亮度调到一半了」。没做成、只做了一部分，或还没确认生效时，直接说是哪种情况、原因和用户接下来能做什么，这时不要说「好了」。
4. 工具查到很多条结果时，说总数和与用户问题最相关的一到三条，其余的说在 Movo 里能看到，不要逐条念。纯问答不要这样说，挑最相关的两三项说完即可。
5. 用户明确要长内容（讲故事、详细讲讲、念全文）时可以说长，用短句。用户明确说「一步步教我」时，先说前两三步，再问要不要接着说；只问「怎么做」时，用两三句把整个做法说完。「介绍一下」「说说」按普通问题处理。
6. 答完就停，不要用提问或提议收尾，比如「要我说得更细吗」「要不要听更细的步骤」「要不要我帮你……」「还有什么需要吗」。只有两种情况可以问：缺关键信息时，在答复里直接用一句话问；用户要长内容、你分段讲时，问要不要接着说。
（角色会话加一句：语气、称呼和人设照旧，只有格式和长短按这里。）
（超级小爱入口：第 4 条去掉「其余的说在 Movo 里能看到」，因为小爱的结果不进 Movo 对话记录。）
```

每条规则为什么这样写：

| 条 | 为什么 |
|---|---|
| 开头 | 只覆盖「格式和长短」，不碰核心规则里「说明证据与不确定性」「部分完成要明说」。点明「前面对话用过表格也一样」，针对历史长答被模仿的问题。告诉模型屏幕上也是这段，免得它把数字写成汉字 |
| 1 | 60 字是大约值，不是硬上限。实测 38% 的回答超过 60 字，但最长约 100 字。行业做法也是给「一两句」而不是字数硬卡 |
| 2 | 取件码、时间、金额是用户要用的；电话、验证码、密码外放念出来有隐私风险（第 7 节第 3 项） |
| 3 | 补上「部分完成」「未确认」，对应核心规则「不把尝试执行当成成功」 |
| 4 | 只用于工具结果；纯问答说「在 Movo 里能看到」是假话，实测 80 次纯问答 0 次这样说 |
| 5 | 明确要长不压短；一步步教先说两三步，研究里有依据（Speechworthy） |
| 6 | 追问写在答复里才会被念出来，配合 3.1 拿掉 `ask_user`。结尾提议是第 7 节第 2 项 |

**这一稿和第三轮实测稿（v4）的差别**（实施时用代码导出的原文回归过，见第 11 节）：
- 开头加了「前面对话里用过标题、列表或表格也一样」；
- 第 6 条改成「答完就停」，并列出不要用的提议句式。只有缺信息和分段讲长内容两种情况可以问。
- 第 5 条写明只有「一步步教我」才分段；只问「怎么做」时用两三句说完。否则菜谱会被讲到一半就停下来问「要不要接着说」。

### 2.4 缓存（实测）

**怎么测的：** 用 `cache_probe.py` 先发一次「预热」请求，再发「探测」请求，看命中多少缓存 token。每组 3 次。

**接口的缓存行为：**
- 接口按前缀自动缓存，整次请求约 11050 个输入 token；
- 工具定义（约 7000 token）排在系统提示**之后**。证据：系统提示开头一变，命中就是 0。

| 情况 | 命中 |
|---|---|
| 同一次任务内的下一轮（请求完全相同） | 11008（约 100%） |
| 文字轮 → 下一次文字轮 | 约 2000–2400（约 20%） |
| 语音轮 → 下一次语音轮（A） | 约 2000（18%） |
| 文字轮 → 语音轮：A | **0** |
| 文字轮 → 语音轮：B / C | 约 2000 |

**结论：**
1. **跨任务本来就只命中约 20%，三种布局都一样。** 环境信息里的当前时间精确到分钟，每次任务都不同；工具定义和全部对话历史排在它后面，每次任务都要重算。这是现状。
2. **A 只在「文字轮之后紧接的第一个语音轮」比 B 少约 2000 token**；之后连续的语音轮和 B 一样。
3. **对速度的影响很小。** 全命中 2.12 秒、命中约 20% 2.32 秒、0 命中 2.30 秒（4 次中位）。在这个接口上，缓存主要影响费用。
4. **拿掉 `ask_user`（3.1）不增加任何缓存损失。** 工具定义本来就排在当前时间后面，跨任务每次都重算；同一次任务内工具列表不变。

只有 ChatGPT 订阅那条路径设了 `prompt_cache_key`，Anthropic 路径没设 `cache_control`。这两条没实测。

「当前时间排在工具和历史前面」影响所有对话的缓存，单独列在第 9 节，不混进本方案。

### 2.5 对业务的影响（实测）

除标明的以外，都是第三轮规则稿 v4、A 布局，每场景 5 次；最易出格式的 4 个场景各 10 次。

| 检查项 | 结果 |
|---|---|
| 会不会少查、少调工具 | 不会。电量、使用时长、通知、看微信、天气：各写法第一步调的工具相同或相近 |
| 文字轮 | A、B 不动文字轮；C 会让文字回答变长（不选） |
| 普通问答长度 | 中位 59 字，最长 101 字（现在中位 203 字） |
| 操作和失败后的长度 | 中位 43 字，最长 90 字 |
| 带 Markdown | 1/94，出在历史里已有长篇表格的场景，靠 3.2 的去格式兜底 |
| 取件码 | 10/10 说了 |
| 电话 | 没问时 0/10 念；问了 5/5 照说 |
| 纯问答说「在 Movo 里能看到」 | 0/80 |
| 缺信息时追问 | 4/5 在答复里问、会念出来；1/5 用了卡片（3.1 解决） |
| 部分完成、未确认 | 如实说。例如：「闹钟已交给系统时钟，但我回读时没看到明早 7 点这条，没法确认它真的设上了。麻烦你打开时钟看一下，如果没有，我马上再设一次。」（60 字）同场景现在的提示写了 165 字、分好几段 |
| 英文 | 159–216 个字符（约两三句）；现在 278–591 个字符 |
| 以问句结尾 | 22%，多是「要我细说火候和分量吗」这类提议。最终稿第 6 条已收紧，待回归 |

**还没测、要在实施时补的：**
- 角色会话；
- 真实的多步操作手机任务；
- 带引用的联网搜索回答；
- 有记忆和技能上下文时；
- 小爱入口；
- 豆包实际语速。

## 3. 不靠模型自觉的三处改动

### 3.1 语音轮不给模型「弹卡片提问」这个工具

- **改法：** `ToolEnvironment` 加一个「这一轮回答会被念出来」的标记，语音轮让 `ask_user` 不可用（`MetaToolProvider.kt:142` 附近）。模型缺信息时只能在答复里直接问，问题会被念出来；你说的下一句就是回答。
- **为什么不直接用现成的 `interactive = false`：** 它还会让审批卡直接返回「无法确认」，会影响手动审批模式。这里只关提问卡片。
- **缓存：** 零额外损失，见 2.4 第 4 条。

### 3.2 念之前去格式（保险）

- **改法：** 新增 `VoiceSpeechText.normalize`，放在 `VoiceReplyContent.body` 里，**只影响送去念的文字，屏幕上仍是原文**。全部是固定的文本替换，不调模型、不改写、不截断。尽量复用仓库里现成的 GFM 解析器。

| 正文里有 | 念成 |
|---|---|
| 标题 `#`、粗体或斜体标记、列表符号和编号、引用 `>` | 去掉符号，只念文字 |
| 链接 `[文字](网址)` | 念「文字」 |
| 裸网址 | 不念 |
| App 插的引用 `[[1]](网址)` 和末尾「来源：」列表 | 不念 |
| 行内代码 | 只念里面的内容 |
| 代码块 | 「代码在屏幕上」 |
| 表格 | 「表格在屏幕上」 |
| 表情 | 去掉；但 ℃、¥ 这类符号保留，不能按符号类别一刀切 |

**边界情况要有单测：**
- 小数 2.5；
- 时间 7:00；
- 范围 10-20；
- `3*4`、`file_name`；
- 「温度>30」；
- 正文里本来就有「|」；
- **去完格式成了空串时**，改念「回答在屏幕上」。否则引擎不回调「播完」，会话会卡在「正在回答」。

**要跟着改的测试：**
- `VoiceReplyContentTest`；
- 真机验收 `VoiceAcceptanceInstrumentation.kt:200-204`，检查改成「念的 == 去格式(正文)」。

### 3.3 超级小爱入口也算语音轮

- **改法：** 不改跨进程协议，直接用已有的 `handoff.source == "xiaoai"` 判断，把这一轮当语音轮。语音段用小爱版本，第 4 条不提「在 Movo 里能看到」。小爱念之前也过一遍 3.2。
- **代价：** 小爱入口里的拍照翻译之类，回答也会变短（第 7 节第 4 项）。

## 4. 模型怎么知道是语音轮

模型自己判断不出来：你说的话转成文字后，和打字发的消息完全一样。是 App 判断，再通过系统提示告诉它。

**链路（代码核实）：**

1. 你在语音模式里说完一句，`VoiceSessionManager.kt:280` 用 `sendVoiceMessage` 把它发出去，带上本次语音会话的编号 `voiceSessionId`。打字发出的消息没有这个编号。
2. 编号跟着任务请求进入运行时（`AgentAppState.kt:1738`）。
3. 运行时据此设 `voiceConversation = voiceSessionId 不为空`（`AgentRuntimeRunExecutor.kt:239`），交给拼提示词的 `AgentPromptBuilder`。
4. 改后判断条件变成「`voiceSessionId` 不为空，或者 `handoff.source == "xiaoai"`」。

| 情况 | 算不算语音轮 |
|---|---|
| 聊天页语音、唤醒词、系统助理、长按悬浮球、展开卡里的语音 | 算 |
| 超级小爱交给 Movo | 现在不算，改后算 |
| 语音模式里点「临时键盘输入」后打字 | 不算。点键盘会先退出语音（`AgentChatInputBar.kt:168`） |
| 文字任务执行中用语音补一句 | 不算。并进那次文字任务，结果也不念 |
| 语音轮跑到一半退出语音 | 仍按语音轮答完；退出后不念，只显示 |
| 任务中途进程被杀、重启后恢复 | 只恢复文字，不重新念（恢复数据里不存语音标记） |

## 5. 不做的事

| 做法 | 不做的理由 |
|---|---|
| `max_output_tokens` 卡长度 | 设 60 时实测返回空正文；违反「不得无提示截断」 |
| `verbosity=low` | 实测不稳，「详细讲讲」反而从 757 字变成 1400 字；只有 OpenAI 系列有这个参数 |
| 念之前再调一次模型改写成口语 | 多一次调用；语音方案 §5.6 规定不另用模型重写 |
| 语音时降推理、换小模型 | `P0能力验证.md:96` 禁止 |
| C 布局 | 改了文字轮现有表现，换来的缓存收益可忽略 |
| 本次顺手调整「当前时间」的位置 | 影响所有对话，要单独评估（第 9 节） |

**2. 回归实测**

用 2.3 的最终原文跑 `run_eval.py`，每场景 5 次，最易出格式的场景 10 次。通过标准：
- 普通问答中位 ≤ 70 字、最长 ≤ 120 字；
- 操作后中位 ≤ 50 字；
- 带 Markdown ≤ 1%（剩下的由去格式兜底）；

- 「详细讲讲」≥ 200 字；
- 以问句结尾的比例按第 7 节第 2 项的决定核对。

**3. 小米真机**

如果设备上有超级小爱，再从小爱说一句。

## 7. 要你定的事

1. **屏幕上显示什么？**
   - A）就是念的这段短文字，详情看执行卡；
   - B）模型另写一份详细版只给屏幕看；
   - C）模型照常写完整回答，屏幕显示全文，只念前一两句，并说「其余在屏幕上」。

   我倾向 **A**。B 要定格式、做解析，模型多写一份更慢。C 不违反现有约束，但要等完整回答写完才开口，比 A 多等，念的也不是专门为听写的。A 的代价是纯问答时屏幕上也只有短答案，想看详细的要再问一句「详细说说」。
2. **结尾可不可以主动提议下一步？**
   - A）不提议，只有分段讲长内容时问「要不要接着说」（2.3 第 6 条）；
   - B）允许一句具体的提议。实测 22% 的回答会以「要我细说火候和分量吗」这类结尾。

   我倾向 **A**，更短，也符合你说的尽量简短。
3. **电话、验证码、密码念不念？** 我倾向**只在你这句话明确要时才念**，避免外放时被旁人听到。
4. **超级小爱入口也按语音轮跑？** 我倾向**要**，代价是小爱里的拍照翻译等也会变短。
5. **角色会话在语音时，长短和格式按语音规则，语气和人设照旧？** 我倾向**这样**。
6. **念之前去格式（3.2）？** 我倾向**做**，内容不变，只是不念符号。

3.1「语音轮不给弹卡片提问的工具」是修一个会冷场的问题，我直接做，不作为选项。

## 9. 单独提出的问题（不在本次范围）

**当前时间排在工具和对话历史前面，跨任务缓存只有约 20%。**
- 现状：每次新任务，工具定义（约 7000 token）和全部历史都要重算。这不是语音的问题，所有对话都一样。
- 影响：主要是费用（实测对速度影响不到 0.2 秒），对话越长越明显。
- 可能的改法：把时间挪到工具和历史之后。但之前把时间放在用户消息开头，模型把它当成了你说的话（`AgentPromptBuilder.kt` 有注释），需要单独设计和实测。你要的话我另写一份。

## 10. 以后可以再做

- **边生成边按句念：** 现在要等整段生成完才开口。这是开口前要等多久的主要原因，回答变短并不能缩短这段等待（实测生成耗时基本不变）。
- **长任务的一句口播（「我去设置里看看」）：** 和「只念 LLM 正文」的约定冲突，要你另外拍板。
- **设置里加「简短 / 标准」两档：** 等确实有需要再加。

## 11. 实施记录（2026-10-06，分支 `feat/voice-brevity`）

### 改了什么

| 方案 | 代码 |
|---|---|
| 语音轮的标记 | 新增 `SpokenReply`（无 / Movo 语音 / 超级小爱），由 `RunRequest.spokenReply` 根据 `voiceSessionId` 和 `handoff.source` 得出，不改跨进程协议 |

### 方案外的两处顺带改动

- **`monitor_stop` 的工具描述**：「先用 ask_user 问停哪个」改成「先问用户停哪个」。工具描述是固定文字，不能按语音轮切换；文字轮的用法分节里仍明确写着用 `ask_user`。这是文字轮唯一一处措辞变化。
- **「工具结果与提问」分节**：改为只要有任何工具可用就注入。原来是 `tool_search`、`ask_user` 都不可用时整节消失，语音轮拿掉 `ask_user` 后，在没有可加载的按需工具时会把「unknown 要先确认」这类通用规则一起丢掉。
