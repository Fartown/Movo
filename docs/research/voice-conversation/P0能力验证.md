# 连续语音 P0 能力验证

日期：2026-09-22。依据：本轮真实服务请求、小米 15 云真机录屏、SDK 事件、物理麦克风回录和安装包校验。任务是验证 [主方案](../../solutions/voice-conversation.md) 的可行性，产品源码未修改，没有发布新版本。

**结论：DeepSeek + 火山独立 TTS 的实际出声链路成立；完整连续语音方案尚未通过。外放插话的近端保真、准确停声、自动端点和首声目标仍是实施门槛。**

## 2. ASR：分句、流结束和用户说完是三个不同事件

用合成的普通话 PCM 以实时速度调用真实接口，包含短命令、自然问句和停顿补话。这里是 API 输入测试，不是自动端点或真实用户麦克风验收。

| 样本 | 最终文本 | 首个 definite | 客户端尾包 | 服务端最终帧 |
|---|---|---:|---:|---:|
| 短命令 | 停 | 2.197 s | 3.986 s | 4.178 s |
| 问句 | 请用一句话解释什么是回声消除。 | 4.912 s | 6.842 s | 7.168 s |
| 补话：两句中间增加 1.2 s 静音 | 请帮我设置一个提醒。时间改成明天上午9点。 | 3.666 s | 9.306 s | 9.490 s |

以上时间相对各请求开始，包含测试音频长度和预设尾部静音，**不是识别延迟排名**。三次均建立 WebSocket，正常返回完整文本；最终帧发生在客户端显式尾包之后。补话样本首句先产生 definite，后续文本仍继续到达。

因此本地端点仍不可省：不能拿 definite 自动提交整个用户轮次，也不能等服务端最终帧来代替客户端决定何时发尾包。900 / 1500 ms 等设计初值尚未经过真实 VAD 和本地提交控制器验证，本轮没有证明这些阈值达标。

证据：[ASR 原始汇总](../../../tmp/tasks/2026-09-22-voice-p0-validation/api/P0-ASR-r1/evidence/summary.json)、[音源及哈希](../../../tmp/tasks/2026-09-22-voice-p0-validation/api/fixtures/manifest.json)。

## 3. TTS：独立 SDK 能出声，但播放控制不能只看返回值

基线运行初始化成功；麦克风首 8 秒回录送真实 ASR，识别出了“这是语音能力验证，今天我们检查真实声音播放、暂停后继续以及用户插话时立即……”。这证明扬声器实际播放了目标内容。

同次实验 `SESSION_FINISHED` 为 3.199 s，`PLAYER_FINISH` 为 14.507 s，相差约 **11.31 s**。合成结束后仍可能有大量内容在播放，不能据此启动续听空闲计时或把下一槽归入已结束状态。

| 控制 | 实际观察 | 判定边界 |
|---|---|---|
| 暂停 / 恢复 | 两条命令均成功；暂停中段 1.15 s 麦回录未识别出文本；之后继续播放 | 精确停声 ≤300 ms、恢复无字词重播尚无充分证据，INCONCLUSIVE |
| 停止 | 暂停后同步停止约 2.24 ms 返回，观察到本轮结束未重启旧播放 | 命令耗时不是实际停声耗时；新旧 engineGeneration 交替压力测试未执行 |
| SDK 播放参考 | 暂停期间 PLAYER_DATA 停止回调；正常运行还包含静音 PCM | 直接拼接文件会压掉暂停间隔，不能当成连续的实际扬声器时间线 |

云机 source 6 回录存在持续底噪，原始 RMS 不能区分语音和噪声。已按回调时间重建参考并做 400–3600 Hz 相关分析；暂停轮全局相关系数绝对值约 0.416。参考尾位置估计不能替代实际停声点：无硬件时间戳、无独立近端说话源、没有足够次数计算 P95。

证据：[真实播放](../../../tmp/tasks/2026-09-22-voice-p0-validation/device/TC-P0-SDK-BASELINE-r1/run.json)、[暂停分析](../../../tmp/tasks/2026-09-22-voice-p0-validation/device/TC-P0-SDK-PAUSE-r1/evidence/output/reference-review.md)、[停止记录](../../../tmp/tasks/2026-09-22-voice-p0-validation/device/TC-P0-SDK-STOP-r1/run.json)。

## 4. AEC：近乎静音不能作为成功依据

配对实验固定 `VOICE_COMMUNICATION`（source 7）、mode 0、同一文本、音量和物理输入路由，仅切换系统 AEC。

| 条件 | 全段回录 RMS，PCM16 原始刻度 | 首 8 秒真实麦回录 ASR |
|---|---:|---|
| AEC OFF | 2.73 / 32768 | 无文本 |
| AEC ON | 2.28 / 32768 | 无文本 |

两边均近乎静音。系统音频状态确认 OFF 无活动 AEC、ON 有活动 AEC，source 7 使用 VOIP_TX 并有 NS 效果；但没有独立近端阳性声源，不能判断用户声音是否也被吞掉，不能把 source 6→7 的差异归因于 AEC 开关。

**结论为 INCONCLUSIVE，外放双讲仍未验收。** 本机扬声器回采能够测试远端回声，但不能同时充当与播放参考独立的近端用户声源。下一轮必须提供可控的独立声源，分别测近端单讲、远端单讲、双讲，验证近端保真、误触发和实际让声时间；也需覆盖音量变化及耳机路由。不会因这个缺口自动切换供应商或改成手动发送。

必要性复核：证据不足不能推出必须新增 SAMI 授权。官方豆包 Dialog SDK 已有 `PARAMS_KEY_ENABLE_AEC_BOOL` 和 `PARAMS_KEY_AEC_MODEL_PATH_STRING`，示例随录放配置开启内置 AEC。本轮实际链路为独立 ASR 2.0（`volc.seedasr.sauc.duration`）与 TTS 2.0，尚未验证 Dialog 的音频能力能否在保留 DeepSeek / 本地 Runtime 的条件下复用。停止 SAMI/RTC 开通候选，先核对现有能力和集成边界。[官方 Dialog Android SDK](https://docs.volcengine.com/docs/DoubaoVoice/endtoend-full-duplex-android-sdk-documentation?lang=zh)

后续补测已经找到并运行 **O2.0 Dialog 客户端 TTS 委托模式**，可保留外部答案来源；默认云回复仍被生成并有协议用量。它纠正了“整个端到端 SDK 都无法保留 DeepSeek”的过度排除，实际播放、AEC 与计量边界见独立的 [DialogSDK复用验证](DialogSDK复用验证.md)，不改写本节历史 ASR/TTS 实验结果。

证据：[OFF](../../../tmp/tasks/2026-09-22-voice-p0-validation/device/TC-P0-SDK-AEC-OFF-r1/run.json)、[ON](../../../tmp/tasks/2026-09-22-voice-p0-validation/device/TC-P0-SDK-AEC-ON-r1/run.json)。OFF 用例 PASS 仅指配对基线成功采集，不表示 AEC 效果通过。

## 5. DeepSeek → TTS：能工作，最终正文后播报的时延有压力

本机三次真实 DeepSeek 请求均正常完成，完整答案耗时 2.05–3.04 s。随后在手机中发起模型请求，把同一份最终正文直接送给官方 SDK，进行两次实测。真实麦回录也识别出回答内容。

| 手机同进程链路 | r1 | r2，修正报告环境后重新执行 |
|---|---:|---:|
| 模型请求 → 完整正文 | 2.917 s | 2.435 s |
| 模型请求 → SDK 开始播放回调 | 3.524 s | 3.186 s |
| 模型请求 → 首段明确语音位置估计 | 4.047 s | 3.716 s |

最后一行使用 SDK 首段明确语音的 300 ms 波形与真实麦回录匹配，局部相关系数分别约 0.545 / 0.405。它是 **有声片段起始位置估计**，不是首个可听音素的硬件时间戳；也不能把播放器回调当作实际出声。r1 以 600 / 1000 ms 窗复核位置差约 1.4 ms，支持匹配位置，但不消除采集时钟偏差。

这两次都从模型请求开始，**不含用户说完后的端点等待、ASR 收尾、Runtime 准入、真实上下文与工具耗时**，样本数也不支持 P50 / P95。现有“无工具短问答 P50≤2.5 s、P95≤4 s”的整轮目标没有达标证据，不能照此承诺体验。

设计处理：保留最终正文后播报作为正确性基线，但不再视为已满足自然对话时延的交付结论。先在集成链路测足够样本并分解耗时；若最终生成占据主要预算，重新评审明确支持的稳定文本增量播报及供应商适配范围。不得通过换模型、关闭用户思考设置、提前播放可被改写的正文或用提示音冒充答案首声达标。

证据：[本机模型请求](../../../tmp/tasks/2026-09-22-voice-p0-validation/api/P0-DEEPSEEK-r1/evidence/summary.json)、[手机 r1 对齐](../../../tmp/tasks/2026-09-22-voice-p0-validation/device/TC-P0-MODEL-TTS-r1/evidence/output/first-audio-analysis.json)、[手机 r2 对齐](../../../tmp/tasks/2026-09-22-voice-p0-validation/device/poc-r2-environment/TC-P0-MODEL-TTS-r2/evidence/output/first-audio-analysis.json)。

## 6. 兼容性和后续门槛

官方 arm64 两个原生库的 ELF LOAD 对齐均为 16384，探针 APK 通过 16 KB zipalign 检查，并在 Android 15 / target 36 上完成真实初始化、合成与销毁。本机实际内存页为 4 KB，**不能据此宣称真实 16 KB 设备兼容通过**。独立构建出现 D8 对 Kotlin 2.4 元数据版本的警告；本轮运行成功，产品 Gradle、混淆和发布构建仍需集成后检查。

| 门槛 | 当前状态 / 必须补齐的证据 |
|---|---|
| DeepSeek 与独立 TTS 组合 | 已实证可工作，不绑定豆包聊天模型 |
| ASR 提供识别分句与流结束信号 | 已实证；自动提交策略未验收 |
| 用户说完与补话 | 实现端点控制器后，覆盖句中停顿、短命令、尾包后补话、无声与噪声，核对只提交一次 |
| 外放自然插话 | 缺独立近端声源与双讲保真，不能通过 |
| 停止和跨槽隔离 | 暂停/恢复/停止命令可运行；实际停声、无重播、新旧代次交替未通过 |
| 首声性能 | 本轮约 3.72–4.05 s 的手机组件链估计尚不含端点，整轮目标未通过 |
| 后台与路由 | 未测试隐藏浮窗后的后台音频焦点、FGS 生命周期、锁屏、耳机切换 |
| 完整产品 | 唤醒连说、自动发送、免触屏三轮、Runtime 准入与工具执行尚未集成验收 |

下一步的优先级是近端声音与双讲、端点控制器、完整链路时延。没有通过这些门槛前，不应再发布一个仅“能录音、能转文字”的包并称为连续语音助手。
