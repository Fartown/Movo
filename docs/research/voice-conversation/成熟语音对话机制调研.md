# 成熟语音对话机制调研

调研日期：2026-09-22。方法：读取产品官方帮助、接口文档、官方开源代码；没有把竞品文档当作本次亲测结果。本文为 [Movo 连续语音对话方案](../../solutions/voice-conversation.md) 提供外部依据；当前代码另见 [语音对话现状与链路调研](语音对话现状与链路调研.md)。

## 1. 正常语音助手的交互基线

用户开始一次语音会话后，正常路径是：说话、自然停下、助手回答并发声、继续说下一句；无需每句话重新唤醒或点击发送。用户还应能在助手说话时插话、暂时静音、结束会话，知道当前是否正在收音。

| 官方对象 | 已核实的公开行为 | 对 Movo 的启示 |
|---|---|---|
| ChatGPT Voice | Voice 用于来回交谈，Dictation 用于转写后检查和编辑；语音会话有麦克风静音和退出控制，可边听边说 | 必须区分“语音对话”和“语音听写”的入口及发送规则 |
| Gemini Live | 用户可以直接说话打断回答，补充细节或换话题；提供字幕和中断设置 | 打断是会话基本动作，字幕应跟随对话，不应成为必须手工发送的草稿 |
| OpenAI Realtime | 自动判断轮次、生成响应和中断响应是分别控制的能力 | ASR 完成不能单独承担整场对话编排 |
| LiveKit Agents | 分别处理轮次检测、结束等待、打断、误打断恢复 | 一个固定录音超时不足以覆盖自然对话 |

来源：[ChatGPT Voice 官方帮助](https://help.openai.com/en/articles/8400625-voice-mode-faq)、[Gemini Live 官方帮助](https://support.google.com/gemini/answer/15274899?hl=en)、[OpenAI VAD](https://developers.openai.com/api/docs/guides/realtime-vad)、[LiveKit Turns](https://docs.livekit.io/agents/logic/turns/)。这些是官方行为说明；没有据此声称所有噪声、长停顿和机型下都能正确判断。

## 2. “说完了”至少涉及三种不同信号

| 信号 | 回答的问题 | 不能据此推出什么 |
|---|---|---|
| 语音活动检测 VAD | 当前是否有人声，最近何时停止发声 | 用户有没有想完、后面是否还要补一句 |
| ASR 分句或最终转写 | 某段音频对应的文字是否稳定，识别流是否结束 | 整个用户轮次是否结束；业务信息是否齐全 |
| 轮次结束判断 EOT | 现在是否应把发言交给助手处理 | 任务一定能直接执行，不需要助手追问 |

OpenAI 提供按静音切分和按语义判断两种模式；后者可对拖尾、犹豫多等一会儿。LiveKit 将声学、语义信号与有上下限的等待结合。这支持一个设计判断：**用声音决定时间边界，用识别和语义辅助等待，不要求用户把任务参数一次说全。** [OpenAI VAD](https://developers.openai.com/api/docs/guides/realtime-vad)、[LiveKit Turn detector](https://docs.livekit.io/agents/logic/turns/turn-detector/)

例如“帮我设个提醒”停下，应提交后问“什么时候”；“帮我设个……提醒，明天九点”中间的犹豫，应尽量留在同一轮。标点来自识别模型，不能作为唯一发送开关。

## 3. 打断不是只取消一个网络请求

OpenAI 的 WebSocket 客户端负责自己的播放缓冲，因此中断时需要停音、记录已播放位置，并处理未播放回答在会话里的表示。Gemini Live 同样要求客户端收到中断后停止本地音频并清理待播队列。这证明“服务端停止生成”与“用户立刻听不到旧话”是两个不同动作。[OpenAI Realtime conversations](https://developers.openai.com/api/docs/guides/realtime-conversations)、[Gemini Live capabilities](https://ai.google.dev/gemini-api/docs/live-api/capabilities)

Movo 的设计需要同时覆盖：

1. 用户开始讲话时先让出声音，保留其开头音频。
2. 确认是真正插话后，取消旧合成、清播放器、拦住迟到结果。
3. 根据用户新话区分“停止朗读”“取消任务”“补充/改问”；已经执行的工具结果不能假装撤销。
4. 后续上下文区分“模型生成了什么”和“扬声器播到了哪里”。播放进度只是可听输出的估计，不证明用户主观听清。

LiveKit 还处理短应和和误触发后的恢复；这意味着咳嗽、噪声或一声“嗯”不宜一律永久销毁旧回答。[LiveKit interruption tuning](https://docs.livekit.io/agents/logic/turns/tuning/)

## 4. Android 音频是独立的工程约束

Android 的 AEC 可以关联到指定 `AudioRecord` 的 audio session，设备是否支持、是否默认启用都需要查询。API 存在不等于目标音频路由下效果合格。[AcousticEchoCanceler](https://developer.android.com/reference/android/media/audiofx/AcousticEchoCanceler)

播放前需要请求音频焦点，并处理失焦。target API 35 及以上时，请求焦点要求前台顶层应用或前台服务；Movo 当前 target 为 36。[Manage audio focus](https://developer.android.com/media/optimize/audio-focus)

麦克风前台服务受 `RECORD_AUDIO` 和 while-in-use 限制，后台新启动有约束；不能把注册了默认助理角色理解为无条件取得所有特权。[Foreground service types](https://developer.android.com/develop/background-work/services/fgs/service-types#microphone)

其他应用抢占输入时，录音可能仍在运行却收到静音；输出焦点与输入竞争是不同机制。通话、耳机切换和录音被系统静音需要独立观测。[Sharing audio input](https://developer.android.com/media/platform/sharing-audio-input)

播放位置可依据 `AudioTrack` 的帧计数/时间戳估算；写入播放器的字节数不能当作已播出的字节数，flush/stop 后还要处理计数重置。[AudioTrack](https://developer.android.com/reference/android/media/AudioTrack)

## 5. 技术路线与可复用依赖

| 路线 | 适用性 | Movo 的判断 |
|---|---|---|
| 豆包 ASR → 既有 Agent → 豆包 TTS | 分层可控，保留模型 BYOK、工具与历史 | 推荐；需要补齐端侧会话编排与音频处理 |
| 端到端实时语音模型 | 提供原生语音交互及轮次能力 | 会改变当前模型与工具协议；本次不作为替换现有 Runtime 的前提 |
| 整套 LiveKit Agents | 有成熟轮次、打断和语音管线 | 官方主要接入在 Python/Node agent 环境；不是把 SDK 放进 Android 就能复用现有本地工具 |
| 本地 VAD + 有界等待 + ASR 辅助 | 不新增云端语义服务依赖，端侧及时响应 | 首选落地基线；必须用中文长短停顿集衡量误截断，不把规则称为通用语义理解 |
| 语义 EOT 模型 | 改善想词、拖尾、多从句的轮次边界 | 列为同一端点接口的评估候选；需确认 Android 部署、体积、推理时延和中文效果再决定 |

Sherpa 官方 `v1.13.8` Kotlin API 已提供 Silero/Ten VAD 配置及逐帧检测入口，正好与当前 KWS 使用版本一致；这证明有可复用 API，未证明 Movo 包内已有 VAD 模型或真机性能达标。[固定版本 Vad.kt](https://github.com/k2-fsa/sherpa-onnx/blob/v1.13.8/sherpa-onnx/kotlin-api/Vad.kt)、[Sherpa VAD 文档](https://k2-fsa.github.io/sherpa/onnx/vad/index.html)

LiveKit 当前音频 EOT 文档包含中文支持，但其云服务/CPU 运行说明不能代替 Android ARM 可用性证明；不直接搬用其性能数字或自动模型切换策略。[LiveKit Turn detector](https://docs.livekit.io/agents/logic/turns/turn-detector/)

## 6. 豆包接口：已查清与未查清

初稿曾按可播报短句调用HTTP流式TTS。后续完成火山专项调研和方案复审，首期已统一为 **现有ASR + Movo/DeepSeek + 官方独立TTS SDK**，不再把HTTP合成器与AudioTrack作为并行必做实现。详细选型及边界见 [火山语音能力与复用选型](火山语音能力与复用选型.md)、[方案复审记录](方案复审记录.md)。上文AudioTrack仅是通用机制例子，不代表SDK已经暴露相同游标。

ASR连接成功不能证明TTS资源/音色可用；实际凭据权限、停止时延、恢复位置和播放回调语义仍需调用及声学验证。本轮没有使用凭据发起TTS请求。[当前独立TTS SDK](https://docs.volcengine.com/docs/DoubaoVoice/bidirectional-streaming-tts-android-sdk-interface-documentation?lang=zh)

首次HTTP/web读取ASR与双向TTS详情页只得到JavaScript外壳，初查过程保留在 [vendor-docs.md](../../../tmp/tasks/2026-09-22-voice-conversation-design/vendor-docs.md)。后续同日已用浏览器读取官方正文并静态查看官方Android demo，因此更新以下结论：

- `definite`表示稳定识别分句，不等于用户完整turn或识别流末包；`end_window_size`指定静音强制分句，不能据此承诺语义判停。
- 继续由本地轮次判断显式结束ASR输入；最终文本范围、补话和尾包时序仍需真实协议帧验证。
- 独立TTS SDK提供合成会话、暂停/恢复和播放回调；合成结束不等于播放结束，取消合成不等于旧缓存已停止。
- 不新增未经验证的ASR参数；SDK适配器的停播屏障、回调身份、目标系统兼容和AEC仍列为P0门槛。

官方入口：[ASR API](https://docs.volcengine.com/docs/DoubaoVoice/LargemodelstreamingautomaticspeechrecognitionAPI?lang=zh)、[TTS SDK](https://docs.volcengine.com/docs/DoubaoVoice/bidirectional-streaming-tts-android-sdk-interface-documentation?lang=zh)。官方文档快照和demo见 [后续调研证据](../../../tmp/tasks/2026-09-22-volcengine-voice-research/)。

## 7. 调研收敛

可确定的产品原则是自动轮次交接、真实声音回复、连续会话与自然插话。具体毫秒阈值、AEC 路由和豆包账户权限不是外部文档能替 Movo 验证的内容。

据此，新方案采用分层语音管线，并将端点、声音输出、回声与插话列为同一完整交付的验收条件。详细状态机、接口改动、参数初值、验证工作包见 [主方案](../../solutions/voice-conversation.md)。
