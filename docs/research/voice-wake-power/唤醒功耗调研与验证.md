# 唤醒词功耗调研与验证

> 时间：2026-09-23。核心代码提交 `a0e87e0`（`fix(voice): cut wake-word battery drain ...`），已随 PR #3 合入 main，合并提交为 `e2adea8`。
> 本文汇总结论、关键数据和出处。原始证据（截图、dumpsys、日志、脚本）在本机 `tmp/tasks/`，该目录被 `.gitignore` 排除，只存在于执行机器上，索引见第 8 节。

## 1. 结论

1. **整夜耗电的原因是息屏时麦克风常开**。录音期间 audioserver 以 Eta 的 uid 持有 `AudioIn` 部分唤醒锁，手机无法休眠。用户实机一晚「保持唤醒状态」8 小时 41 分。已改为息屏暂停。
2. **第三方 App 不能用 DSP 低功耗唤醒**。Android CDD 明文禁止，厂商也没有面向普通 App 开放。高德同样没用。
3. **高德省电靠的是只在界面可见时监听**，不是更省电的收音技术。同样条件下，两者的录音开销估算几乎相同。Eta 已新增「监听范围」设置，默认与高德一致。
4. **Eta 的唤醒模型计算量明显更大**。噪声环境下，唤醒线程 CPU 约为高德的 15 倍。安静环境下能量门控能把这部分降到同一量级。
5. **截图里的「应用所耗电量 30.08%」是占当晚总耗电的份额**，不是电池容量的 30%。

## 2. 问题与口径

- **用户实机**（HyperOS 电量详情）：Eta「应用所耗电量 30.08%」，「保持唤醒状态 8 小时 41 分 27 秒」，发送移动数据 1.64 MB，接收 1.28 MB，省电策略为「无限制」。
- **百分比口径**：AOSP 设置 `BatteryDiffEntry.java` 中是 `mPercentage = (mConsumePower / mTotalConsumePower) * 100.0`，注释为 "Gets the percentage of total consumed power"，即该应用耗电除以这段时间所有条目的总耗电。
  - 出处：https://raw.githubusercontent.com/aosp-mirror/platform_packages_apps_Settings/main/src/com/android/settings/fuelgauge/batteryusage/BatteryDiffEntry.java （2026-09-23 核对，第 183 行）
  - 小米没有公开自己的口径，这里按 AOSP 定义推断。
- **「保持唤醒状态」**对应 AOSP 的 `usage_type_wake_lock`（英文 "Keep awake"），即 PARTIAL_WAKE_LOCK 的累计时长。
- **移动数据很少**，排除了网络类原因。

## 3. 根因

### 3.1 代码（改动前）

- `EtaWakeWordService` 是 `microphone` 类型前台服务，`START_STICKY`。
- `SherpaWakeEngine` 让 `AudioRecord`（16 kHz、`VOICE_RECOGNITION`）常开，每 100 ms 把音频送进 sherpa-onnx 1.13.8 的 zipformer 开放词表 KWS（约 330 万参数，transducer + beam search）。
- 没有任何息屏、静音或前后台处理。
- AudioFlinger 的 `RecordThread` 在有活跃录音时调用 `acquireWakeLock_l()`，tag 为 `AudioIn`，并把客户端 uid 写进 WorkSource。出处：https://android.googlesource.com/platform/frameworks/av/+/refs/heads/main/services/audioflinger/Threads.cpp

### 3.2 云真机实测（小米 15，Android 15，HyperOS OS2.0.105.0，电池 5400 mAh）

每个窗口 10 分钟，用 `dumpsys battery unplug` 进入电池统计。mAh 是 batterystats 按机型功耗表估算的，不是电流实测，只适合横向比较。云机常接电源，机房噪声底约 -25 dBFS。

| 窗口 | 包 / 屏幕 / 唤醒 | 唤醒线程 CPU | Eta 估算耗电（分项） | 归属 Eta 的 AudioIn |
|---|---|---|---|---|
| W1 | 改动前行为 / 亮 / 开 | 31 480 ms（约 5.2% 单核） | 8.80 mAh（cpu 2.82，audio 5.98） | 有 |
| W2 | 门控 v1 / 亮 / 开 | 2 160 ms | 6.10 mAh（cpu 0.13，audio 5.98） | 有 |
| W3 | 门控 v1 / 亮 / 关 | 无线程；进程 50 ms | 不在耗电列表 | 无 |
| W4 | 门控 v1 / 灭 / 开 | 2 300 ms | 7.23 mAh（audio 5.99，wakelock 1.12） | 9 分 53 秒（98%） |
| W5 | 门控 v1 / 灭 / 关 | 无线程；进程 80 ms | 不在耗电列表 | 无 |
| W6 | 息屏暂停 / 灭 / 开 | 0 ms；进程 50 ms | 不在耗电列表 | 无 |

- **唤醒关闭时，Eta 没有其他后台耗电**（W3、W5）。
- **这台云机本身息屏不休眠**：W5 的 uptime 也是 100%，所以「常听阻止休眠」没法在云机上直接对比。W4 能证明的是：息屏期间录音唤醒锁 98% 的时间归到了 Eta。

## 4. 改动与验证

### 4.1 能量门控（`WakeEnergyGate`）

每 100 ms 计算一次音量，只有在噪声底之上明显变大时才送进模型。第一版在云真机上出现回归，已修正。

| 版本 | 参数 | 结果 |
|---|---|---|
| v1 | 高于噪声底 8 dB，预录 0.6 s，收尾 1 s，无放行 | 85% 音量 0/6 命中（未门控为 3/3），100% 音量 0/3 |
| v2（已提交） | 6 dB，预录 1 s，收尾 2 s，噪声底 ≥ -50 dBFS 时放行 | 85% 音量 3/3，70% 音量 3/3 |

**v1 回归的原因**：用同版本 KWS 模型离线回放云机录音（`offline/exp_datacenter.py`）。

- **吵闹环境**：机房噪声底稳定在 -25 dBFS，唤醒词峰值 -17.5 dBFS，只高出约 7.5 dB，门一次都没开。
- **安静环境**：门能打开，但 KWS 在唤醒词峰值后约 1.3 s 才给出结果，1 s 的收尾把命中时刻截掉了。
  - 离线模拟（`offline/exp_quiet.py`）：噪声底 -65 / -55 dBFS，信噪比 4–25 dB 共 10 组。v2 全部命中，每 75 s 送进模型约 3.2–4.2 s。v1 在信噪比 ≤ 10 dB 时全部漏唤醒。非唤醒词语句没有误唤醒。

**限制**：云机房没有安静环境。v2 在安静条件下的门控路径只有离线证据，吵闹环境下它等同于不门控。

### 4.2 息屏暂停监听

收到 `ACTION_SCREEN_OFF` 时暂停引擎并释放 `AudioRecord`；`ACTION_SCREEN_ON` 后，如果不在对话中就恢复。前台服务和已加载的模型保留。

云真机验证：

| 项 | 结果 |
|---|---|
| 息屏 10 分钟 | 归属 Eta 的 AudioIn 从 9 分 53 秒（W4）降到 0，唤醒线程 CPU 从 2 300 ms 降到 0（W6） |
| 亮屏后 | 1 秒内恢复录音；85% 音量 3/3 |
| 快速切换 | 息屏、亮屏交替 3 次正常，无崩溃，进程未重启 |

**没能测到**：「对话中息屏」。云机没有配置豆包凭据，对话没有真正开始。

**与语音对话的关系**：同一时间只有一方收音。所有语音对话入口都先调用 `EtaWakeWordService.pauseWake`，等唤醒录音释放（最多 1 s）后才打开对话 SDK 的录音。结束时要确认 `DoubaoDialogEngine.hasOpenAudio()` 为 false 才恢复唤醒。

### 4.3 下拉快捷开关（`EtaWakeTileService`）

- **点按**：开关唤醒。**长按**：进入「语音与唤醒词」设置页。
- **开启时的中转**：麦克风前台服务只能在界面可见时启动，所以经透明的 `WakeTileBridgeActivity` 中转，服务转入前台后自动关闭（最多 3 s）。

云真机 7 项全部通过：
- 从桌面开启、进程被杀后冷启动开启，中转界面都在 1 s 内关闭，录音 `silenced:false`，85% 音量 3/3；
- 关闭、长按跳转、无权限跳转设置页，都符合预期。

**HyperOS 的限制**：控制中心不显示磁贴副标题，只能看到图标和 On/Off。

### 4.4 监听范围（设置项）

- **仅在 Eta 打开时**（默认）：任何 Eta 界面都不可见 1.5 s 后暂停，回到 Eta 自动恢复。
- **亮屏时（含其他 App）**：可选。
- 两种范围在息屏时都暂停。

**未在真机验证**：云机测试开始时 ADB 断连，用户随后要求不测，仅有单测覆盖。

### 4.5 用量日志

`voice / wake.usage`，同时写入 logcat（`Wake usage:`）。每累计 10 分钟音频，以及每次监听结束时各打一条。字段：
- `audio_s`：采集时长；
- `model_s`：实际送进模型的时长；
- `gate_opens`：开门次数；
- `cpu_ms`：唤醒线程 CPU 时间；
- `floor_db`：当时的噪声底。

## 5. 行业对比

### 5.1 高德地图 17.00.0.2005（「小德小德」）

**静态分析**：官方 APK，证书 `CN=minimap, O=autonavi`，SHA-256 `b36c0b80…2e3e`。

| 项 | 发现 |
|---|---|
| 引擎 | 阿里达摩院 NUI SDK，`libnui.so` 约 7 MB |
| 唤醒模型 | `assets/mandarin/kws.bin`，619 KB。kaldi nnet1，16 bit 量化，40 维 fbank，NN 每 3 帧计算一次；有本地二级复核和云端复核（500 ms 超时） |
| 录音 | 16 kHz，`MIC` 音源，每次读取 50 ms |
| 启停 | `VUIStateManager.onPause()` 调 `releaseAudioRecord()`；App 进入后台（所有 Activity onStop，包括息屏）即释放麦克风 |
| 系统能力 | 没有监听 `SCREEN_OFF`；没有使用 `AlwaysOnHotwordDetector`、`SoundTrigger`、`VoiceInteractionService` |
| 默认值 | 唤醒开关 `voice_wakeup_switch` 默认 false |

**同一台云真机实测**（与 Eta 同样的测法）：

| 状态 | 是否在听 |
|---|---|
| 首页前台、亮屏 | 在听（`MIC` 16 kHz，AudioIn 归高德 uid） |
| 回到桌面 | 按 HOME 的瞬间停止录音 |
| 前台时息屏 | 息屏瞬间停止 |
| 导航中、前台 | 在听 |
| 导航中回到桌面 | 导航继续，但停止录音 |

- 唤醒率：首页前台，85% 音量，TTS 合成的「小德小德」4/5。
- 设置页（我的 → 设置 → 导航设置 → 更多设置 → 辅助功能 → 语音唤醒小德）没有任何耗电或可用范围说明。

**10 分钟前台亮屏对比**：

| | 高德 H1 | Eta 改动前（W1） | Eta 门控（W2，安静时） |
|---|---|---|---|
| 唤醒相关线程 CPU | `amap-record` 2 090 ms（约 0.35% 单核） | 31 480 ms | 2 160 ms |
| 录音分项估算 | 6.10 mAh | 5.98 mAh | 5.98 mAh |
| 什么时候在听 | 仅前台亮屏 | 始终 | 始终 |

高德 H1 的 uid 总估算为 42.4 mAh，其中还包括屏幕、GNSS、地图渲染等，与唤醒无关。

### 5.2 其他应用与平台

- **华为官方**：「百度地图/高德地图App开启了语音助手功能，会占用麦克风进行录音，导致无法唤醒小艺。」https://consumer.huawei.com/cn/support/content/zh-cn16073412/
- **Amazon Alexa App**：只在 "the phone is unlocked and the Alexa app is open on the screen" 时才能免手唤醒。https://techcrunch.com/2020/07/07/amazon-adds-hands-free-alexa-to-its-alexa-mobile-app/
- **百度地图、腾讯地图、讯飞输入法、喜马拉雅等**：没有找到关于唤醒耗电或后台、息屏可用范围的官方说明。详见 `web-research.md` 第 2 节。

### 5.3 DSP / 系统 hotword 通路

- **CDD**：`[9.8/H-1-9] MUST NOT allow a user-installable application to provide the hotword detection service.` Android 14 / 15 / 16 三版一致；15 版已于 2026-09-23 核对。https://source.android.com/docs/compatibility/15/android-15-cdd
- **SDK**：`AlwaysOnHotwordDetector`、`HotwordDetectionService`、`SoundTriggerManager` 不在公开 SDK 中（本机 `platforms/android-36/android.jar` 中不存在）。
- **权限**：`CAPTURE_AUDIO_HOTWORD` 和 `MANAGE_SOUND_TRIGGER` 为 `signature|privileged|role`，唯一授予它们的 role 是 `systemOnly` 的 `SYSTEM_AMBIENT_AUDIO_INTELLIGENCE`。https://android.googlesource.com/platform/packages/modules/Permission/+/refs/heads/main/PermissionController/res/xml/roles.xml
- **国内厂商**：
  - 华为 `@ohos.ai.intelligentVoice` 是系统接口；
  - 小米、OPPO、vivo 只开放技能和 ASR/TTS；
  - 荣耀 Voice Kit 可以注册自定义关键词，但音频仍由 App 自己用 AudioRecord 采集，不走 DSP。
- **小爱接管**：需要 Root + LSPosed，且锁定超级小爱 7.13.32.0016；它接管的是小爱识别后的请求，不能在息屏时唤起 Eta 自己的界面。

### 5.4 纯软件 KWS 的数据

- **Google 流式 KWS**：在 Pixel 4 上每 20 ms 音频处理耗时约 0.5 ms 起，折算约占单核 2.5%–8%。Eta 的 5.2% 在这个区间内。https://ar5iv.labs.arxiv.org/html/2005.06720
- **录音本身才是耗电大头**：18 台 Android 真机外接电源实测（Appl. Syst. Innov. 2018, 1, 8）。
  - 连续录音、不做信号处理时续航中位数约 40 h，加算法后约 28 h；
  - 8 k / 16 k / 22.05 k / 48 kHz 采样率对功耗无统计显著差异。
  - https://mdpi-res.com/d_attachment/asi/asi-01-00008/article_deploy/asi-01-00008.pdf
- **zipformer KWS 的召回率**：k2 官方数据显示，未针对性 finetune 的开放词表 zipformer KWS 在真实场景召回率只有 46%–57%，官方原文为 "very poor"；finetune 后可到 95% 以上。https://k2-fsa.github.io/sherpa/onnx/kws/index.html
- **不采信**：网上流传的「百度 12–15 / 讯飞 18–22 mAh/24h」「Pixel 4a 14.2 mAh/24h」等数字，来源已失效或疑似批量生成。

## 6. 未验证项与已知问题

- **监听范围**没有在真机上验证。
- **安静环境下的门控**只有离线模拟证据。
- **「对话中息屏」**没有真实构造出来。
- **整夜实际放电**没有测到：云机常接电源，而且本身息屏不休眠。需要在用户实机上过一晚，看电量详情和 `wake.usage` 来确认。
- **唤醒率**：本文实测时默认词还是「小王同学」，当前模型未针对该词 finetune，云机上 A 包 70% 音量只有 1/3 命中。PR #3 合入前默认词已改为「小O小O」，尚未按同一协议做真机唤醒率回归，也未针对该词 finetune。这可能比功耗更值得优先处理。
- **`ToolCatalogUiTest.everyRuntimeToolAndDisplayedCardHasASpecificIcon`** 在 main `65d1674` 上就失败，与本次改动无关，未处理。
- **v2 测试包混入了其他任务的改动**：10:53 发给用户的 v2 release 测试包，以及云机测试用的 C、D、E 包，混入了同一工作区里另一个任务（助手统一交互、锁屏）当时尚未提交的改动。
  - 这些改动没有碰唤醒引擎、息屏逻辑，也没有改 `VoiceSurfaceTracker` 的逻辑（只改了注释），所以上述唤醒结论仍然成立。
  - 11:58 发出的 v3 只包含 main `65d1674` 加本次唤醒改动，SHA-256 `15f6fe59…e98c`。

## 7. 后续方向

1. **换更省计算的一级唤醒**：目的是缩小噪声环境下约 15 倍的 CPU 差距。要保留自定义唤醒词，需要找支持自定义词的小模型或商业 SDK（阿里 NUI、讯飞等）；也可以给默认词单独训练小模型，与 zipformer 组成两级。建议先离线评估计算量和召回率，再决定。
2. **针对默认唤醒词 finetune**：出发点是唤醒率，不是功耗。代价是默认词和自定义词的效果会分成两档。
3. **不建议的方向**：
   - 找厂商开放 DSP：CDD 禁止；
   - Root 装成系统特权应用：只解决抢麦克风，不解决耗电；
   - 降低采样率：实测对功耗没有影响。
