# 对话存储重构方案（待 review）

> 2026-10-06。手机和电视共用这套存储，改完两边一起受益。依据是对现有代码的四路调研，文中行号对应 `feat/tv-flavor` @ `8b402d7`（已于 `c530ffb` 合入 main）。

## 0. 一句话

**数据库是唯一的真身：发生一件事写一行，用到什么读什么，同一件事只存一份。**

| | 现在 | 改后 |
| --- | --- | --- |
| 保存 | 任何变化都把**所有对话**删光重写 | 只写发生的那一件事（插一行或改一行） |
| 启动 | 把**所有对话**的全部内容读进内存 | 只读对话列表和当前那一个对话 |
| 一轮执行存几份 | 最多 8 份 | 1 份 |
| 执行中写库 | 每个事件先同步写库，模型等着 | 写库排队在单独线程，不挡模型 |

## 1. 现在的问题（都有代码依据）

1. **界面侧整份重写。**
   - `AgentAppState` 里有 26 处会调用 `persistConversations()`，触发者包括发消息、运行结果、改标题、切换对话、监听事件等。
   - 每次都走 `ConversationDao.replaceAll`：四张表删光，全部重新插入，长文本的分块也一起删了重写。
   - 电视上一次要 1.5–5.6 s，整个过程独占 SQLite 唯一的写锁。
2. **启动整份读入。**
   - `AgentConversationStore.loadSnapshot` 把每个对话的消息、模型历史、日志都读出来并解码，放进 `conversationsById`。
   - 对话数和消息数都没有上限；电视上隔 2 分钟以上再唤醒就新开一个对话，所以只增不减。
   - 电视 debug 包打开时主线程要等 2.2 s。
3. **Runtime 侧也是整份写，而且挡着模型。**
   - `AgentRunCheckpointStore` 的每次写库都用 `runBlocking` 包着，在执行线程上同步完成。
   - 每个事件要先写进库，才会发给界面；模型流的回调要等这次写完。
   - 每次工具调用之后，`saveTranscript` 都把这一轮到目前为止的完整记录重新编码、重写一遍，所以一轮里越往后写得越多。
4. **同一轮执行存了 8 份。** 运行结果在被界面确认（ack）之前，下面这些同时存在：
   - 界面的消息行 `conversation_messages`；
   - 模型历史 `history_json`；
   - 完整日志 `journal_json`；
   - Runtime 的进行中记录 `runtime_inflight_runs`（记录和上下文快照）；
   - 进行中事件 `runtime_inflight_events`；
   - 结果 `runtime_results`；
   - 外部运行的归档 `runtime_archive_*`；
   - 内存里的回放事件。
5. **交接流程绕。** 一轮执行的结果走这样一条链：Runtime 存进结果表 → 发给界面 → 界面合进内存 → 整库重写 → 回 ack → Runtime 删结果和进行中记录。进程被杀后，还要用另一套恢复逻辑把事件重放回界面。
6. **其他问题：**
   - `conversations.history_json` 早已废弃，但还在；
   - 分页查询 `conversationsPage` 从没用过；
   - 列表没有预览字段，搜索靠扫内存里全部对话的内容；
   - 消息里的图片以 base64 内嵌存储，所以需要分块；
   - 备份直接序列化数据库表对应的类，表一改备份就跟着变；
   - 没有导出表结构（`exportSchema = false`），没法用 `MigrationTestHelper` 测迁移。

## 2. 目标结构

> 2026-10-06 修订：原稿想把界面行和模型消息合进一张 `conversation_items` 表。细看数据后改为“两本账”，理由有三：
> - 模型那边一条“回答”消息里，同时带着正文和这一步的所有工具调用；界面上它会拆成思考、正文、每个工具各一行，两边是多对多，合进一张表映射很绕。
> - 两边存的东西本来就不同：界面行存摘要、步骤视图、耗时；模型消息存完整的工具结果，并且已脱敏。
> - 现有的 `conversation_messages` 表字段已经合适，不用换表，迁移只剩一件事。

### 2.1 表

**`conversations`：对话目录，不变**
- 新增 `updated_at` 索引，侧栏按它分页查询。
- 侧栏预览不加新列：列出对话时顺带查每个对话的最后一行，用现成的 `(conversation_id, sort_index)` 索引。
- `history_json` 已经废弃，留着不用（SQLite 删列要重建整张表，不值得）。

**`conversation_messages`：界面时间线，表结构不变，写法改为一行一行写**
- 每个对话里按 `sort_index` 排序。
- 追加时取当前最大值加 1024；在中间插入（比如执行中插入补充指令、监听事件）时，取前后两行的中间值。没有空隙了才给这个对话重新编号，这种情况很少见。

**`conversation_model_messages`：发给模型的消息，新表，一条一行**
- 字段：`id`（自增）、`conversation_id`（删对话时一起删）、`log`（`history` 或 `journal`）、`seq`、`run_id`、`message_json`（单条消息，已脱敏，不含图片）。
- 唯一索引 `(conversation_id, log, seq)`。
- 超过 16K 字符时沿用 `agent_text_chunks` 分块，加删除触发器。
- **`history`**：发给模型的历史。每轮执行只往后追加；压缩、删除某一轮、编辑、重新生成、角色扮演修订时，只重写这一个对话的 `history` 行。
- **`journal`**：完整记录，只往后追加。删除某一轮时，只重写这一个对话的 `journal` 行。

**不变**：`conversation_state` 只有一行，记着当前选中的对话；切换对话时只改这一行。

### 2.2 不再使用

- `conversation_context_checkpoints`：迁移后不再读写，下个版本删除。
- App 内对话用到的 `runtime_inflight_runs`、`runtime_inflight_events`、`runtime_results` 和 ack 流程（第 2 步处理）。

小爱、小布这类外部运行用的归档 `runtime_archive_*` 这次不动。

### 2.3 图片

新写入的图片存成文件，消息里只记路径，删除对话时连同文件一起删。旧数据里内嵌的 base64 照样能读，不强制转换。

## 3. 什么时候写什么

| 发生的事 | 写入 | 谁写 | 要不要等 |
| --- | --- | --- | --- |
| 用户发送 | 插入“用户消息”行；`history` 和 `journal` 各追加一行；更新对话的 `updated_at` | App | **等**，只是几毫秒的小事务，写完再开跑。“先把你的话存好再执行”这个保证就保留下来了 |
| 模型逐字输出（文字、思考） | 不写，只在内存里显示 | — | — |
| 一段文字或思考结束 | 插入“回答”或“思考”行 | Runtime | 不等：交给单独的写线程，按顺序写 |
| 工具开始 | 插入“工具调用”行（进行中） | Runtime | 不等 |
| 工具结束 | 更新这一行：状态、结果摘要、步骤视图、`model_json` 补上工具结果 | Runtime | 不等 |
| 补充指令、监听事件、压缩 | 各插一行 | Runtime 或 App | 不等 |
| 模型消息产生（每轮回答、工具结果） | 追加到这一轮的 `history`、`journal` 行，标为“进行中”；一轮结束时转为正式 | Runtime | 不等 |\n| 一轮结束 | 更新对话的 `updated_at`、用量 | Runtime | 不等 |
| 改标题、切换选中、改推理强度 | 改对话那一行，或改设置 | App | — |
| 删除对话 | 删这个对话的所有行和图片文件 | App | — |
| 删除某一轮、重新生成、编辑 | 删掉对应 `seq` 区间的行再追加 | App | — |

**分工：** 执行过程中发生的事，只由 Runtime 写；用户的操作只由 App 写；同一件事不会两边都写。两边在同一个进程里（调研已确认，`AgentRuntimeService` 没有单独进程），共用一个 `ConversationRepository`。

**执行中界面怎么更新：** 不变。界面照样通过 Messenger 实时收到事件，更新当前打开的那段内容。数据库在后台按顺序写，界面不用读库。

**进程被杀之后：** 已经发生的事（界面行和这一轮已产生的模型消息）都已经在库里了，不需要再重放。启动时把还标着“进行中”的那一轮按中断处理：在对话里加一条中断提示，这一轮已产生的模型消息转为正式。写线程里还没来得及写的最后几件事会丢失。

## 4. 什么时候读什么

- **侧栏列表**：从 `conversations` 按 `updated_at` 分页读，用 Room Flow 监听变化。电视上没有列表。
- **打开一个对话**：读最近 100 条，往上翻再读更早的。
- **开跑时给模型的历史**：在后台读当前这一个对话的 `history` 行。
- **搜索**：在数据库里对 `conversation_messages` 的正文和摘要做 `LIKE` 查询，不再扫内存。
- **导出 Markdown**：从数据库读这个对话的全部行。
- **后台监听、通知深链、运行结果属于别的对话时**：直接对数据库读写那个对话，不需要它在内存里。
- **电视**：唤醒时只读最近的那个对话；“看全文”只读最后一条回答。`TvWarmup` 删掉。

`AgentAppState` 改后在内存里只留三样：对话列表、当前打开的那一段、正在执行的那一轮的实时状态。`conversationsById`、`persistConversations`、`AgentConversationStore` 都删掉。

## 5. 旧数据怎么迁移

- 数据库从 23 升到 24：
  - 新建 `conversation_model_messages`。
  - 把 `conversation_context_checkpoints` 里每个对话的 `history_json`、`journal_json`（分块的先拼回来）拆成一条一行写进新表。
  - `conversation_messages` 和 `conversations` 的数据不动，只给 `conversations` 加 `updated_at` 索引。
- 旧的检查点表这个版本保留不删，下个版本确认没问题再删。
- 开始导出表结构：`exportSchema = true`，加上 `schemas/` 目录。先在 23 版导出一份，再做 24。迁移用 `MigrationTestHelper` 测。
- 再用真实数据库在本地验证（不提交进仓库）：电视上那份（19 个对话、860 条消息），以及小米测试机上拉的一份。
- 迁移只在升级后第一次打开时发生一次。电视和小米上都要实测耗时。

## 6. 其他用到对话数据的地方

- **备份**：
  - 新增 v3 格式，用单独定义的备份数据结构，不再直接序列化表对应的类。
  - v1、v2 备份导入时先转换。
  - 导入仍在一个事务里完成，之后界面只需重新读列表。
- **角色扮演**：
  - 角色绑定和候选回复留在 `conversations` 这一行。
  - 开跑前先写好，再开跑（满足“开跑前已落库”的顺序要求）。
  - 改写目标的检查改为查 `conversation_messages`（原来就是这样）。
- **诊断页**：改读新的 `conversations` 表。
- **不受影响**：`conversation_read` 工具（它只读本轮带过去的历史），以及记忆功能（不引用对话）。

## 7. 分四步做（同一个分支，每一步都能编译、单测通过）

1. **存储层**：建新表，写好 `ConversationRepository`（追加、更新、删区间、拼模型历史、分页、搜索），完成迁移，开启表结构导出，补迁移测试和仓库测试。这一步不接入界面。
2. **Runtime 按事件写**：
   - 执行中的事件由 Runtime 通过单独的写线程写入 `conversation_messages`、`conversation_model_messages`；
   - App 内对话不再使用 inflight、results 和 ack 那一套；
   - 启动时把没执行完的那一轮按中断处理；
   - 删掉 `0bebc8e` 里的“异步保存”补丁，恢复“先落库再开跑”。
3. **界面按需读**：
   - `AgentAppState` 去掉全量内存。列表、打开对话、搜索、导出、监听、运行恢复、语音都改成读写数据库。
   - 删掉 `AgentConversationStore`、`persistConversations`、`TvWarmup` 和预读。
   - 重写原来依赖整份存取的 15 个存储测试和 6 个保留测试。
4. **收尾**：备份 v3、诊断页；旧表在下一个版本删除。

**不在这次范围内：** 小爱、小布这类外部运行的归档，以及给对话数加上限。电视每次唤醒新开对话，对话会越积越多；按“不加隐藏策略”的规矩，默认不设上限，以后要的话放进设置里。

## 8. 验收

**性能**：电视 debug 包和正式包、小米手机都要测。

| 指标 | 目标 |
| --- | --- |
| 用户消息落库 | ≤ 50 ms |
| 模型第一轮 | 不再等任何写盘：发出后 ≤ 1 s 开始请求 |
| 一个执行事件写库 | 不挡模型，在执行线程上耗时为 0 |
| 打开 App | 不读任何对话内容 |
| 内存 | 不随对话总数增长 |

**正确性：**
- 进程被杀的时机分别覆盖：刚发出、执行中、写入中。被杀后对话完整，那一轮标为中断。
- 下面这些操作之后接着聊，发给模型的历史都要正确：删除、改标题、删除某一轮、重新生成、编辑、压缩。
- 角色扮演改写、备份导入导出（v1、v2、v3）、后台监听事件、外部运行导入，都要正常。

**回归：**
- 手机，只用小米真机：侧栏、搜索、切换、删除、导出、备份、监听、恢复、语音。
- 电视：跑冒烟用例。
