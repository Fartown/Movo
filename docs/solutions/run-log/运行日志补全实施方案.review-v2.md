## 共识问题（三路一致）

### M1 [P0] 脱敏兑现不了“密码和 Key 不落盘、不导出”（A#1、B#1、C#2）
- **位置**：§0；§5.1 原则 5「磁盘上就不存在密码和 Key」；§5.9 擦除表「之后写入的所有文本」；§5.10 文件头；§5.12 页脚「API Key 和密码不会导出」。
- **问题**：
  1. 擦除表只对之后写入的内容生效。用户原话（“密码是 xxx，帮我登录”）、系统提示词和较早轮次，在密码被识别之前就已经落盘了（三路）。
  2. 配置里的秘密只列了 `apiKey` 和 `customHeaders`，漏了 `extraBodyJson` 和 `customBody`（B、C；已核实 `AgentModelClient.kt:289-291`）。
  3. 只有 `ui_input` 会遮参数。执行卡上已经遮住的几种输入，在日志里却是明文：`browser_act` 的网页输入、`clipboard_write`（sensitive）、读到的敏感剪贴板（A；已核实 `BrowserActTool.kt:129`、`:213`，`ClipboardTools.kt:76-77`、`:161`）。
  4. SECRET 结果只收集了 `outcome.data`，没覆盖 `textBody`、错误文本和摘要（C）。
  5. 按字面替换会被 JSON 转义绕过（A）。
  6. 太短的秘密、编码过或拆开转述的秘密，都不在保证范围内（B、C）。
- **后果**：明文密码写进 `files/run-log`，又随导出发出去，而界面上写着“密码不会导出”。这是错误的安全承诺。
- **建议**：
  - 先把承诺收窄到机制能兑现的范围（A）。
  - 规则改成“执行卡遮了什么，日志就遮什么”，判定一律用执行时已经得出的结论（A）。
  - 补齐秘密来源：`extraBodyJson`、`customBody`、`textBody`、错误文本、摘要（B、C）。
  - 在序列化之前按字段脱敏，同时匹配转义后的形式（A）。
  - 运行结束后，用完整的擦除表把 `steps.jsonl` 整体重写一遍；没走到重写的运行，导出时写明（A）。导出时再全量擦一遍（B）。
  - 要不要加密本机文件，见分歧 4。

### M2 [P0] 模型收到的原图会带出屏幕上的密码、验证码（A#1-6、B#2、C#3）
- **位置**：§2.6 第 2 条「模型自己要的截图原样记」；§5.9；§5.10 文件头。
- **问题**：文本脱敏改不了截图上的像素。`ui_observe` 的敏感度是 PRIVATE 而不是 SECRET，屏幕上显示的验证码、没遮住的密码、令牌，都会原样保存、原样导出。节点文字和监听事件的正文也一样（A）。
- **后果**：文字里遮住了，图片里还在，和“密码已去掉”的说法直接冲突。
- **建议**：页脚和文件头照实写“截图和屏幕文字按模型看到的原样保存，可能含屏幕上显示的验证码等”。要遮挡，只能用执行中本来就有的信息，不能为此额外采集；做不到就不做这个承诺。

### M3 [P0；B 定 P0，A、C 定 P1] 导出的 zip 进公共下载目录，清空和卸载都删不掉（A#3、B#2、C#11）
- **位置**：§5.10 第 5 步 `MediaStore.Downloads`；§4.2「不弹二次确认」；§6.2 第 1 行「能一键清空」。
- **问题**：
  - 每导出一次，公共目录里就多一份含对话和截图的 zip。分享取消了它还在，卸载后也还在，有“所有文件访问”权限的 App 都能读。
  - `clearAll()` 不管这些文件。
  - 方案还绕开了现有的 `CreateDocument` 导出，新加了两条往外发的路径（B）。
- **后果**：用户以为点了清空就没了，完整内容却一直留在公共目录。
- **定级**：取 B 的 P0。理由是这和 M2 叠加后，会长期留下一份可能含凭据的公共副本，而且“清空”给了错误的预期。
- **建议**：存放方式见分歧 3。不管选哪种，§6.2 的处置和页脚都要写清楚，已导出的文件是“不归清空管”还是“清空时一并删除”。

### M4 [P1] 为脱敏提前读当前焦点，违反“不为日志额外读取”（A#2、B#4、C#1）
- **位置**：§5.7「写 `round` 之前……取 `secretArguments`」；§5.9「否则看当前焦点」。
- **问题**：
  - 不带 index 的 `ui_input` 会调用 `focusedInputIsPassword()`，这是一次实时的无障碍查询，纯粹为了记日志。
  - 时机也不对：同一批里先点密码框、再输入时，判定那一刻焦点还没过去。
  - 这次查询可能超出 5ms（三路；已核实 `UiInputTool.kt:111-128`）。
- **后果**：违反你定的原则；该遮的没遮住；拖慢运行线程。
- **建议**：
  - 删掉 `secretArguments`，以及各层的默认实现。
  - `round` 记录里的工具调用只存 id 和名称，参数只在 `tool` 记录里存（A）。
  - `tool` 记录用执行时 resolve 已经得出的敏感度，拒绝路径也要带上。
  - 没走到 resolve 的调用，一律按“判断不了就遮”处理。

### M5 [P1] 被停止或失败的那一轮、失败的重试都不记（A#6、B#3、C#5）
- **位置**：§5.6 `round`「每轮模型成功返回后」；§5.7「只含成功那次尝试」；`run_end` 的字段。
- **问题**：
  - 用户停止或请求失败时，这一轮不写记录（三路）。其实代码里已经有半截思考可以拿（A；已核实 `AgentModelClient.kt:215` 的 `reasoningSnapshot`）。
  - 失败重试的思考会被丢掉（B、C）。
  - 工具已经派发、结果还没返回时，没有任何记录（C）。
  - 图片要到下一次请求才发给模型，工具一返回就记成“模型收到”是不对的（B、C；已核实 `AgentLoop.kt:204`、`:144-147`）。
- **后果**：像 R57 这样停在长时间生成里的情况，还是答不出“停的时候它在干什么”。
- **建议**：
  - `run_end` 加上本轮未完成那次尝试的内容（A）。
  - 每次尝试都记开始、已收到的输出，以及失败或取消的终态（B、C）。
  - 工具记“已派发 / 已返回 / 未知”。
  - 图片分清“工具产出 / 附进请求 / 请求已发出”三种状态。

### M7 [P1] 写入完整性，以及导出、清空、写入之间的一致性（B#6、C#6、C#8、A#14、A#19）
- **位置**：§5.6「队列满了就丢弃」，公共字段只有 `v/t/at/el`；§5.10 直接读目录导出；§5.12 `clearAll()`。
- **问题**：
  - 没有连续序号和缺口标记，丢了几行导出时看不出来。
  - 没规定图片和引用它的记录谁先落盘。
  - 没规定 `run_end` 能不能被丢、导出前要不要等写完（B、C）。
  - 没规定清空、导出、写入同时发生时谁优先（B、C）。A 另指出，清空会把进行中运行的元数据也一起清掉。
  - 导出协程挂在页面作用域上，离开页面就会被中断，留下写了一半的文件（A；已核实 `DiagnosticsData.kt:201`）。
- **后果**：最需要诊断的高负载、进程被杀场景，日志恰好不全，看起来却像是完整的。
- **建议**：
  - 每次运行加连续序号、缺口记录和“已关闭”标记。
  - 图片先写临时文件再改名，然后才写引用它的记录。
  - `run_end` 和导出之前设一道等写完的屏障。
  - 清空和导出都放到同一个写线程上串行执行；清空时保留进行中运行的元数据。
  - 导出放到不随页面销毁的作用域里；失败或取消时，删掉没写完的文件。

### M8 [P1] 暂停、继续、Movo 到前台按墙钟时间推归属（B#5、C#9、A#21）
- **位置**：§5.8「运行外的事件……按墙钟时间落进对应运行」；§5.11 D10。
- **问题**：
  - 暂停和继续发生时，服务明明知道是哪个运行，方案却先丢掉身份、再按时间去推。
  - 新旧运行交替时，两个运行的时间窗会重叠（B）。
  - Activity 到前台只能说明界面到了前台，说明不了是谁操作的，也说明不了任务被打断了。
  - 现成的 `boundRuns()` 就能直接对应运行号（A；已核实 `MemoryDiagnostics.kt:115-134`）。
- **后果**：事件挂到错误的运行上，或者把时间上挨着的事件写成了原因。
- **建议**：暂停、继续、停止和交互都带运行号记录。屏幕、网络、App 前后台这类事件，只作为“同一时间发生的系统事件”列出，不推断是谁做的，也不推断是不是原因。

### M9 [P1] 字段契约和两份数据的对应关系没定义（A#9、C#14、B#6）
- **位置**：§5.6 字段表；`find(runId, startedAt)` 允许 2 秒误差；§5.10 合并。
- **问题**：
  - 字段类型、是否必填、单位、`event` 有哪些种类，都没列全（C）。
  - 运行、轮次、尝试、请求、工具之间怎么对应没定义（三路）。
  - 按开始时间 2 秒内匹配不可靠，准备阶段本身就可能超过 2 秒（A；已核实 `AgentRuntimeRunExecutor.kt:147-154` 的阻塞加载）。
  - 元数据里的工具记录没有调用 id，同一轮里的同名工具会对错（A；已核实 `AgentDiagnosticEvents.kt:11-12`）。
- **后果**：导出时把 A 工具的参数显示在 B 工具下面，或者误报“没有详细日志”。
- **建议**：
  - 用 sealed class 或 JSON Schema 把字段写全。
  - 在元数据的 run 记录里写入详细日志的目录名，导出时按名字精确查找。
  - `tool.started` / `tool.finished` 加调用 id。
  - 写明对不上的记录怎么显示。

### M10 [P1；A 定 P2] 容量和性能的估算没有依据，几个上限不成立（A#13、B#8、C#7）
- **位置**：§5.10「每张约 150KB」；§5.6「200MB」「队列 1,000 条」「已有 24,000 字的上限」；§2.1「≤5ms」。
- **问题**：
  - 截图是全分辨率、质量 95 的 JPEG。主流程核实了真机日志（`.docs/design-restore/device-test/phase2-retest7/logcat_full.txt`）：2 个样本都是 195,405 字节，比 150KB 大约三成，每次运行有几张也没测过。
  - 队列按条数限，不按字节。
  - 进行中的运行不受 200MB 约束（C）。
  - `ToolProjection` 的 24,000 字上限只管 JSON 分支，终端输出这类文本分支没有上限（C；已核实 `ToolProjection.kt:17`、`:48-75`）。
  - 运行线程上还要做解析和擦除，5ms 从没测过（B）。
- **后果**：长任务可能撑爆存储或内存；碰到 200MB 上限时，会把你想看的那次运行淘汰掉。
- **建议**：
  - 先用 R57 类任务和截图多的任务实测。
  - 给单次运行和队列都设字节上限，触顶时写明截断了什么。
  - 明确“20 次”和“200MB”冲突时以哪个为准。
  - 日志这一侧自己给文本结果设上限。

### M11 [P1；A 定 P2] 测试证明不了三条底线（A#15、B#9、C#13）
- **位置**：§6.3 U3、V2、V4。
- **问题**：
  - 没有测试能证明这三条：记日志时设备读取次数零增加；导出内容和模型实际收到的一致；各类敏感内容都没落盘。
  - V4 用端到端总耗时对比，测不出 5ms 级别的差异。
  - 缺停止、重试、进程被杀、清空和导出同时发生等用例。
- **后果**：测试全过了，仍然可能多读了设备、漏了密码、丢了失败现场。
- **建议**：
  - 加三道必过门槛：
    1. 监听所有设备后端调用，开、关日志前后的调用次数必须完全一致。
    2. 用测试 provider 记下实际请求，和导出内容逐次比对。
    3. 构造一批敏感语料，直接扫描私有目录、zip、md、jsonl 和图片，出现明文就判失败（B）。
  - Recorder 每个入口自己计时，把 p50、p95、max 写进 `runlog.run_closed`（A）。
  - 补上上面列的异常用例。

### M12 [P1；A 定 P2] 没有版本演进和回滚办法（A#18、C#10、B#6）
- **位置**：§5.6「v1」；§5.13 工作包。
- **问题**：

- **建议**：

## 共识问题（两路提出）

### M6 [P1] 没记模型每次请求实际收到的完整输入（B#3、C#4）
- **位置**：§5.6 `history` 只记条数和估算 token，`tools` 只记名字；§5.7 只在开始时记一次系统提示词。
- **问题**：每轮请求前，上下文都要经过历史注入、压缩、角色投影和动态工具目录（已核实 `AgentLoop.kt:93-108`），系统提示词也可能更新（C）。只靠开头的提示词加每轮输出，反推不出模型当时看到的是什么。
- **A 路为什么没提**：A 只从隐私角度提了系统提示词（见 M14），没有覆盖“能不能还原输入”这一点，不是持不同看法。
- **后果**：一旦涉及历史、压缩或工具变化，“它看到了什么”这一问就答不出来。
- **建议**：每次请求记四样：相对上一次新增的消息、整份请求的哈希、工具定义（有变化时）、图片清单。压缩或投影之后，记一次完整上下文。复用已有的请求对象，不为日志另外读任何东西。（主流程补充：按差量记，避免每轮全量记录让体积随轮数平方增长。）

### M20 [P2] SECRET 结果把所有 ≥4 个字的字符串都放进擦除表，误伤面大（A#16、C#2）
- **建议**：由工具声明哪些输出字段是机密，只擦这些字段的值。

## 单路发现（已核实）

### M13 [P1] “复制到剪贴板”改成带内容的摘要版（仅 A#4）
- **核实**：`DiagnosticsData.kt:347-349` 没有设置 `EXTRA_IS_SENSITIVE`；R57 粘贴原文只有约 7KB 就被截断了（`.docs/run-log/R57-…md`）。
- **问题**：
  - 剪贴板从“只有元数据、可以随手转发”变成了带屏幕文字和输入内容，输入法和剪贴板历史都能看到。
  - 改动依据“完整内容超过系统剪贴板上限”不成立：7KB 远低于上限，截断更可能发生在粘贴目标那一侧。
- **建议**：复制保持现在的元数据版不变；要发给开发者，走导出文件。

### M14 [P1] 系统提示词里有长期记忆，`run_start` 的图片可能是相册照片，都没告知用户（仅 A#5）
- **核实**：`AgentPromptBuilder.kt:198-203` 会注入 `<memory_core>`。
- **问题**：你确认的导出范围是“对话、思考、屏幕内容”，不包括长期记忆和照片；页脚也没写本机会保存这些内容。
- **建议**：
  - 字段表写清 `images` 存的是什么。
  - 记忆段默认只记字数和标题；要导出全文，就写进页脚和文件头，并请你确认。
  - 页脚同时说明本机保存的范围。

### M15 [P1] “只记已发生”这条原则的写法前后矛盾（仅 A#7）
- **核实**：方案 §0、§5.1 写的是「模型没看到的，不进日志」，但 §2.1 第 6 问又要记暂停、停止、Movo 到前台、锁屏、断网，这些模型都没看到。§8 删掉了悬浮球展开收起，却保留了暂停和继续，标准不统一。
- **建议**：改写成两条可判定的规则：
  - **可以记**：模型的输入和输出、工具的参数和结果、用户对 Movo 的操作、Movo 和系统已经产生的事件。
  - **不可以**：为记日志新增任何读取，包括截图、查无障碍树或焦点、读其他 App 或设备的状态。
  - 悬浮球展开收起要不要恢复，见分歧 5。

### M16 [P1] 线上已有的漏洞：被拒绝的密码框输入以明文进了聊天记录（仅 A#8）
- **核实**：`ContractTool.kt:34` 在 resolve 拒绝时返回 NORMAL。被拒的 `ui_input` 因此不进敏感名单，参数原样写进 checkpoint 和对话库，下一次运行还会作为历史发给模型。`clipboard_write`（sensitive）也一样（`ClipboardTools.kt:161`）。
- **建议**：单独修：拒绝路径保留 resolve 已经得出的敏感度；`ui_input` 和 `clipboard_write`（sensitive）在解析失败或被拒时，一律按敏感处理。可以随 P1 一起提交；不在本方案里修的话，就加一条跟进项。

### M18 [P2] 停止来源分得太细（仅 A#11）
- **核实**：外部进程发来的取消可以用 `sendingUid` 识别（`AgentRuntimeService.kt:2612`）。
- **建议**：收敛到 4 个汇聚点（App 内、悬浮球、通知、运行时自身），外部进程靠 `sendingUid` 推出来。这样 4 个界面文件和 2 个 Xposed 钩子都不用改。

### M19 [P2] 导出菜单 3 项，和“导出只有一个”矛盾（仅 A#12）
- **核实**：§0 写着「导出也只有一个」，§5.10 却列了 3 项。
- **建议**：详情页只留“导出完整日志”和原样的“复制”；“导出为 Markdown”要么保持元数据版，要么删掉。

### M21 [P2] 能不能拿到思考全文，取决于服务商（仅 A#17）
- **核实**：`OpenAiResponsesProvider.kt:284-285` 两种思考流都收（全文和摘要）。
- **建议**：`round` 记一个 `reasoning_kind`（全文 / 摘要 / 没有），验收写明用默认模型。

### M22 [P2] “最近 20 次”把自动运行也算进去，想看的那次会被挤掉（仅 A#20）
- **核实**：`withRun` 包住了所有操作，包括后台监听唤醒、上下文压缩和改写回复（`AgentRuntimeRunExecutor.kt:61-66`）。
- **建议**：用户发起的运行和自动运行分开计数，或者在详情页提供“保留这次”。

### M23 [P2] 复用：现成的事件流没列为候选（仅 A#21）
- **核实**：`AgentRuntimeRunExecutor.kt:387` 的 `acceptEvent` 已经逐条收到交互、监听、用量这些事件。
- **建议**：这几类直接从事件流里记，`AgentLoop` 只补采参数、交给模型的原文、图片和系统提示词。

### M24 [P2] 改动总览有遗漏，图和正文不一致，代码基线已前移（A#22；C 路执行时证实了基线前移）
- **问题**：
  - 改动总览漏了 `AgentRuntimeSession.kt`，`Diagnostics` 放在哪个文件也没写。
  - 元数据里记 `endpoint_host`，和 `MemoryDiagnostics.kt:182` 那条“不记 URL”的注释冲突；`run_start` 里已经有了，元数据可以不记。
  - §4.1 里 runStarted 和 runEnded 由谁发出，和 §5.7 写的不一致；图里也没有清空链路。
  - 方案写的是“当前分支落后 main 两个提交”，现在已经是 4 个：c7fc32f 之后 main 又合入了 `4f6a935`、`379a8ab`。要改的 `AgentRuntimeService.kt` 等 6 个文件都有变动，例如 `requestStop` 从 `:1104` 挪到了 `:1117`。

## 分歧与待确认

1. **总结论**：A 认为“有条件通过”（先改 #1–#9 再开工），B、C 认为“需重大修改”。

2. **自动诊断保留多少**：
   - B：一期整个删掉。

   - C：删 D2 和所有因果结论，保留事实统计。
   - **主流程倾向**：A/C。保留的几条只是日志里事实的汇总，不推断原因，读长日志时有用。
   - **需要你定。**
3. **导出存到哪、要不要确认**：
   - B：复用现有的 `CreateDocument`，存到用户自己选的位置；分享走私有临时文件；导出前加确认。
   - A 二选一：存到 App 专属外部目录，用 FileProvider 分享；或者继续存下载目录，清空时一并删掉。
   - C：只要求写明“清空不删已导出的文件”。

## Premortem 汇总

1. **三路一致：隐私事故。** 导出包里有密码、验证码或记忆内容，界面上却写着“密码不会导出”；下载目录里的旧 zip 也清不掉。已升级为 M1、M2、M3、M14、M16。
2. **三路一致：关键时刻日志答不上来。** 停在长时间生成里的那一轮、失败的重试、写盘积压时丢掉的几行都没记下来；导出看起来像完整的，或者误报“没有详细日志”。已升级为 M5、M6、M7、M9、M22。
3. **两路（B、C）：两类问题。**
   - 自动诊断把正常操作说成“来回打转”“被打断”，排查方向被带偏。已升级为 M17。
   - 存储被撑爆，或者导出、清空时数据错乱。已升级为 M7、M10。
4. **单路（A）：停止链路改动引入回归。** 有入口漏改、来源标错甚至停不下来；实时焦点查询拖慢每一轮。已升级为 M4、M11、M18。

## 未验证的关键断言

1. 每轮、每个工具的额外耗时 ≤ 5ms：还没实现，也没测过（三路）。
2. 每次运行有几张截图、zip 多大、生成多久：都没实测。单张约 195KB 有 2 个真机样本（主流程补充）。
3. R57 第 21 轮之后的数据：粘贴被截断，无法核对（三路）。
4. 默认模型（Agent Plan，走 `openai_responses`）返回的是思考全文还是摘要（A）。
5. 下面几条平台行为，都没在 HyperOS 真机上验证（A、C）：
   - MediaStore 返回的 URI 能不能直接分享。
   - 下载目录里的文件卸载后是否保留、其他 App 能不能读。
   - App 专属外部目录能不能用 adb 拉取。
6. `allowBackup="false"` 在 Android 12 以上能不能同时阻止换机迁移（A）。
7. Android 自带的 org.json 和 JVM 单测用的 org.json，对 `/` 的转义是否不同（A）。
8. 用户 10-06 确认导出范围时，是否包含了“公共下载目录长期保留”“截图可能含凭据”这些完整告知（B）。
9. §5.8 列出的停止入口是否穷尽（B）。
10. 正常一次运行不到 300 条记录（A）。
