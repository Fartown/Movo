## 共识问题（三路一致）

### V1 [P0] “密码、Key 不写入”做不到（A#1、B#1、C#1）
- **位置**：§0「会遮的……运行结束后再整体擦一遍」；§5.1 `request_start`「新增的消息（含系统提示词）」；§5.3；§5.5 页脚「配置的 Key 和密码框输入不会写入」。
- **问题**：
  - 遮挡只做在 `tool_start` / `tool_end`。模型的工具调用参数和工具原始结果，会作为下一次请求的“新增消息”再写一遍，而且是明文（A，已核实 `AgentConversationCodec`）。
  - 擦除只在结束时生效，挡不住第一次落盘（三路）。
  - 用户原话里的密码，在“不推断”的前提下识别不出来（B、C）。
  - 进行中、被杀的运行，带着没擦的内容也能导出（三路）。
  - `browser_act`、`clipboard_write` 的值没进擦除表；“工具声明机密字段”在代码里没有这个机制（A、C）。
- **后果**：按设计，明文密码会写进私有目录、进到导出包，而页脚写的是“不会写入”。
- **建议**：
  - 在序列化之前统一遮，`request_start` 里的工具参数和结果用同一套规则。
  - 擦除表每写一行就生效，结束重写只负责补擦“值出现之前写下的行”。
  - 没擦完的不允许按完整日志导出（具体见分歧 4）。
  - 原话、模型正文、截图里的秘密如实告知会原样保存，不承诺能遮掉。

### V3 [P1] 工具开始在返回后才记（A#3、B#6、C#4）
- **问题**：工具在执行中被停止或进程被杀时，`executeTool` 不会返回，按方案就不会有开始记录，参数和开始时刻都没有。代码里执行前本来就有 `ToolStarted` 事件（已核实 `AgentLoop` 先发事件后执行）；参数在 `ToolCall` 里，不在 `ToolResult` 里。
- **建议**：执行前写 `tool_start`，可能是密码的字段先不写；返回时写 `tool_end`，按执行时的判断补记这几个字段（遮或不遮）。只有开始、没有结束的，如实记成“未返回”，不去推断它有没有生效。

### V4 [P1] 记下的请求不是模型实际收到的（A#4、B#4、C#3）
- **问题**：
  - 各服务商还会再转换：`ResponsesRequestBuilder`、`AnthropicMessagesProvider.buildRequestJson`、`RequestBodyMerge` 合并 custom body，可能改掉 model、messages、tools（B、C，已核实）。
  - 请求也不是只往后加：每回合会删掉观察截图消息，工具定义会原地替换系统消息，角色会话每轮都重新投影（A）。
  - 门槛 2 的比对基准没有定义。
- **建议**：差量改成“相同前缀条数 + 其后全部”，每条带上整份请求的哈希；重试只记“和上次相同”。在哪一层记录，见分歧 2。

### V5 [P1] 重试和每次尝试的边界不清（A#14、A#15、B#5、C#5）
- **问题**：
  - `AgentModelExecutionException` 带的是整次运行累计的思考，失败那次尝试的思考已经被丢掉，正文根本不在异常里（三路，已核实）。
  - Q 编号在 `AgentModelRetry` 里分配，不在清单里。
  - 压缩请求（`AgentContextCompactor`）和 401 刷新后的重发（已核实）没有记录点。
- **建议**：每次真实发送单独编号；在流式回调里按尝试缓存已收到的内容，丢弃之前先写下来；压缩和重发也要记；可以复用 `AgentRunCheckpointRecorder` 现成的增量合并逻辑（V20）。

### V6 [P1] 第 6 问答不全（A#2、A#15、B#2、C#6）
- **问题**：
  - 前后台、断网、熄屏是在主线程或系统线程上记的，没有运行号。照“带运行号的记录才同步”，这些都进不了日志文件，比旧导出（按时间挂进运行）还少（三路）。
  - 补充的话由 `AgentRuntimeService` 经 `session.steer` 发出，不经过 `acceptEvent`（A、B，已核实）。
  - `InteractionResolved` 只带 `requestId`，拿不到作答结果（A、B）。
  - 现有只监听了 `SCREEN_OFF/ON`，没有锁屏状态（B、C，已核实）。
- **建议**：
  - 运行期间发生的全局系统事件，按发生时刻写进所有进行中的运行，标为系统事件，不推断因果。
  - 补充在 Service 记；作答在 `BrokeredUserInteraction` 记。
  - 第 6 问里的“锁屏”改成“熄屏、亮屏”。

### V7 [P1；A 定 P2] 没有字段级定义，有前后矛盾（A#4、A#13、B#3、C#7）
- **问题**：
  - 没有字段名、类型、是否必填、枚举、关联 ID。
  - 三处前后矛盾：参数到底记在 `tool_start` 还是 `tool_end`；`ToolResult` 现在只有 `sensitive` 布尔值，并没有“最终敏感度”；服务地址在 `run_start` 的清单里没有。
  - `meta` 原样同步，会把本机内部 ID（`wire_run`、`conversation`）带进 zip（A）。
- **建议**：在 `RunLogRecords` 里用 sealed class 定义每类记录的字段，方案附一张字段表；改掉矛盾；把 7 个问题逐一对应到具体字段。

### V8 [P1；A 定 P2] 写入、擦除、导出、清空的生命周期（A#11、B#7、B#8、C#8、C#12）
- **问题**：
  - `events.log` 和新日志各有一个写线程，所以“清空和导出排队执行”只对新日志成立。
  - “已结束”标记写在擦除之前还是之后，前后说法不一。
  - 进行中的运行导出时，没有截止点。
  - 先打 zip 会在 `cacheDir` 留一份明文副本。
  - 50MB 的结束重写和打包会堵住唯一的写线程，其他运行的写入跟着排队。
  - `DiagnosticStore` 改名失败时会先删原文件再改名，敏感日志不能照搬这个做法（C，已核实）。
- **建议**：定义四个状态：活动、结束待处理、可导出、失败；导出以固定序号为截止点；清空分别投递给两个写线程，各自只保留进行中的运行；重写分块做，用安全的发布方式；临时文件写明清理时机，并纳入“清空”。

### V9 [P1；A 定 P2] 截断和丢弃，与“能回答 7 问”冲突（A#10、B#7、C#9）
- **问题**：单次运行超过 50MB 后，丢的是结局；`run_end`、结束擦除这类控制记录可能被丢；字段上限按字节，而模型侧上限是 24,000 字符，中文结果会被截。
- **建议**：控制记录不受上限约束；单次超限时先停存图片，文本照写；字段上限按字符算，作用在单条消息上；`run_end` 写明是否完整，以及缺了什么。

### V11 [P1] 测试暴露不了缺口（A#1、A#7、B#9、C#13）
- **建议**：
  - 敏感扫描加四个时刻：第一次写入后、强杀并重启后、导出进行中、焦点判断不了的 `ui_input`。
  - 3 个服务商的真实构造器各比对一次请求。
  - 门槛 1 的监听范围加上 `DiagnosticsEnvironment` 和 `PackageManager`，并定义“关日志”用什么开关（例如注入空的 Recorder）。
  - 补上失败分支：写满、写失败、模型流中断、工具执行中停止。

### V12 [P1；A 定 P2] 导出流程没定（A#12、B#8、C#8）
- **建议**：
  - 顺序沿用现有的“先选位置再写入”，避免出现临时明文副本。
  - 导出任务由 Activity 级的状态持有，不引入后台服务。
  - 补上进行中、成功、失败、取消四种状态。
  - 导出前提示一句会带出哪些内容、这次运行擦完没有；和菜单一起出 Figma 候选稿。

## 共识问题（两路提出）

### V2 [P0；C 定 P0，A 定 P1] “判断不了是不是密码框”在执行结果里不存在（A#1-3、A#7、C#2）
- **核实**：`UiInputTool.resolve` 里写的是 `focusedInputIsPassword() == true` 和 `?.password == true`，判断不了（null）时就当成“不是”，敏感度是 NORMAL。
- **B 路为什么没单列**：B 的 #1 讲的是同一类泄漏，没细分到这一层，不是持不同看法。
- **建议**：resolve 保留三态，经 `CallResolution` 和 `ContractTool` 透出；“判断不了”一律遮；记录侧不重新 resolve，也不查焦点。

### V13 [P1；A 定 P2] 兼容和止损（A#16、C#11）
- **核实**：manifest 只有 `allowBackup="false"`，没有配 `dataExtractionRules`。
- **建议**：没有详细日志时，菜单退回元数据导出，或写明为什么不可用；加一个内部止损开关；把日志目录排除出换机迁移；取消消息没带来源时，按 `sendingUid` 归类。

## 单路发现（已核实）

### V10 [P1] 容量没有推导（C#10；A#10、#11 和 B#7 有部分重叠）
- 按真实任务估算常见值和峰值；入队之前先复制、序列化，这一步就要限额；临时文件也算进预算；磁盘不足时停止记录，并写明。

### V14 [P1] PRIVATE 数据开始落盘，“和对话库一样”不成立（A#5）
- **核实**：
  - 对话库存的转录会把敏感工具的参数和结果换成“未写入持久会话”，图片一律剔除（`AgentConversationCodec`）。
  - `file_read` 遇到绝对路径直接打开（`FileToolBackends.resolveLocalFile`）。
- **问题**：日志会明文保存通讯录、短信、通知、日程、文件、终端输出、相册附图等，其中很多是第三方的个人信息；Agent 自己也能读到日志目录（网页里的提示注入可能借此把内容带出去，按代码路径可达，没在真机验证）。
- **建议**：§2.3 照实写，并请用户重新确认“不加密”；页脚和导出提示逐类写明。要不要最小化、要不要防 Agent 自读，见分歧 5。

### V15 [P1] “顺手修”只修了一条路径（A#6）
- **核实**：
  - `Approval.kt` 在 `interaction.approve` 之后紧接着 `checkCancelled()`；在确认卡上点停止会直接抛出，这条调用不会被登记为敏感。
  - `AgentSensitiveToolPolicy` 的名单里没有 `ui_input`、`browser_act`、`clipboard_write`。
- **建议**：执行前就把 resolve 得出的敏感度登记给循环；或者把这三个工具加进名单（只影响没执行完的调用）。V3 那组真机验收补两例：确认卡出现时点停止；输出被截断的 `ui_input`。

### V16 [P1] 有几处写法会逼实现为日志额外读取或推断（A#7；B#5 提了思考种类）
- **核实**：
  - 远程图片经 `AgentRuntimeImageTransfer` 直接把 URL 传给服务商，Movo 从没下载过。
  - `AssistantBlockKind` 只有 TEXT、THINKING、TOOL_CALL 三种，分不出全文还是摘要。
- **建议**：标题复用 `ToolStarted.argsPreview`；只记原始的思考标记（SSE 事件类型等），不按服务商贴“全文 / 摘要”；远程图片只记 URL；新加的元数据记录不附环境快照；`sendingUid` 只记数值。

### V17 [P1] 擦除表收进 body 的值，会误伤并把 JSON 改坏（A#8）
- **核实**：`CustomBody.value` 是任意 `JsonElement`（`RequestBodyMerge`）。
- **建议**：配置类只收 API Key 和长度 ≥ 8 的请求头值；擦除在解析后的字符串值上做，不碰 JSON 结构。

### V19 [P2] 改动清单和交互图有遗漏（A#14；C 的推演也提到了）
- **问题**：清单里漏了 `AgentModelRetry`、3 个服务商和 `ProviderEvent`、`UiInputTool` 和 `CallResolution`、`ToolContract`、SECRET 工具、`BrokeredUserInteraction`；`AgentAppState` 里实际有好几处 `cancelRun`；记录点要放在 `session.emit` 过滤之前，否则服务销毁时的收尾记不到。
- **建议**：补全清单；交互图补上 `AgentRuntimeService`、`AgentExecutionService`、`DiagnosticsEnvironment` 和清空链路。

### V20 [P2] 漏列了现成的实现（A#15）
- **核实**：`AgentRunCheckpointRecorder` 存在，已经按“轮次 + 种类 + 序号”合并思考和正文的增量。
- **建议**：把它（已收到的部分）、`DiagnosticTraceBuilder.buildRun`（按时间窗挂系统事件）、`AgentConversationCodec.redactSensitiveToolData`（在消息里按调用 ID 遮挡）、`ToolStarted` 都列进 §3，并说明怎么复用。

## 分歧与待确认

1. **总结论**：A 判“有条件通过”（改完 #1–#8 再开工，结构不用推倒），B、C 判“需重大修改”。
   - **主流程倾向**：需重大修改。两条 P0 都动到隐私承诺本身，V3–V9 要改记录时机、边界和生命周期。不过三路都认为整体结构不用推倒，改动都在现有结构里。
2. **请求在哪一层记**：B、C 主张在各服务商完成转换、合并之后、发送之前，记最终请求（去掉鉴权和配置机密）；A 主张以内部的 `ProviderRequest` 为基准，服务商的改写另外单测。
   - **主流程倾向**：B、C。“模型实际收到了什么”只有最终请求能回答，custom body 能改掉 model 和 messages。代价是 3 个服务商各加一个记录点。
   - **需要你定。**
3. **原话等自由文本里的密码**：三路一致，不推断就识别不出来，只能如实告知会原样保存。这不是分歧，列在这里是因为要改承诺的说法。
4. **没擦完的运行怎么导出**：A 主张导出前提示，默认不导出；B 主张下次启动先补完擦除，补失败就禁止导出；C 主张没处理完的不算“完整日志”。
   - **主流程倾向**：B。进程被杀的，下次启动先补擦；进行中的，导出时先对已写部分做一次擦除，并标为“未结束”。
   - **需要你定。**
5. **个人数据和防 Agent 自读**（A#5，A 明确说交给你定）：
   - 个人数据查询的结果：保持原样（与“只记原始日志”一致，靠告知），还是默认只记条数和字段名。
   - 要不要禁止 Agent 用 `file_read` 和终端读 Movo 自己的日志目录。这算一条新的拦截规则，按你的约定，不能默认偷偷加。
   - **主流程倾向**：两项都保持原样、不加拦截，在页脚、导出提示和风险表里写清楚。
   - **需要你定。**
6. **定级不一致**：V2、V7、V8、V9、V12、V13 三路给的级别不同，按规则取有依据的较高一级，原定级已在表中注明。

## Premortem 汇总

1. **三路一致：密码明文被导出。** 卡住或被杀的运行导出后，里面有网页密码、Wi‑Fi 密码、原话里的密码，或者通讯录、聊天截图，而页脚写着“不会写入”。已升级为 V1、V2、V8、V11、V14、V15。
2. **三路一致：关键时刻日志仍然答不上来。** 停在工具执行中，没有参数和开始时刻；模型实际收到的请求、失败那次尝试、补充和作答、前后台和断网都缺；长任务超过上限，丢了结局。已升级为 V3–V6、V9。
3. **两路（B、C）：残缺日志显示为完整。** 写满、写失败或进程被杀之后，导出的日志看起来是完整的。已升级为 V8–V10。
4. **单路（A）：停止链路回归或写线程堵塞。** `cancel(source)` 要穿过很多个类，改动面大；结束重写和打包堵住写线程，导致缺行。已升级为 V8、V18。

## 未验证的关键断言

1. 默认模型（Agent Plan，走 `openai_responses`）返回的是思考全文还是摘要（A、B）。
2. 系统提示词（含长期记忆）、工具定义全量、最大的屏幕元素结果，实际有多大，会不会超过字段上限（A、B）。
3. 一次 R57 类任务的日志体积和截图张数。单张 195KB 有真机日志样本（`image_bytes=195405`，2 张），但分布没有统计（A、B、C；样本由主流程核对）。
4. `allowBackup="false"` 在 Android 12 以上能不能阻止小米换机带走日志目录（A）。
5. 50MB 的结束重写和打包在测试机上要多久，期间写入队列会不会溢出（A）。
6. 长任务中主进程被系统杀掉有多频繁，这决定没擦完的运行有多常见（A）。
7. `file_read` 用绝对路径能不能真的读到日志目录：代码路径可达，没在真机验证（A）。
8. 停止时的转录最终写进对话库、下次又作为历史发给模型：代码路径如此，没在真机验证（A）。
9. 用户确认的导出范围，是否包括第三方个人信息和截图里可能有的凭据（B、C）。
