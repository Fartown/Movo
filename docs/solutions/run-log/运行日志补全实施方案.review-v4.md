## 共识问题（三路一致）

### W1 [P0] 擦除的进程崩溃窗口（C#1 P0、A#18 P2、B#1 P0）
- **问题**：
  - 方案只认“`scrub start` 已写入、没有 `scrub done`”这一种中断。秘密已经确定、但标记还在队列里、写失败、或进程在落盘前被杀，这几种情况重启后都会被判成“已中断、可导出”。
  - 改名失败时如果照常写 `scrub done`，也会被放行（A）。
  - 崩溃后留下的临时文件没人清（A）。
  - 擦除表随进程丢失，没法补擦（B）。
- **建议**：
  - 先同步写下不含秘密的“待擦除”标记，再继续写后面的行。
  - 标记写失败、擦除失败、改名失败，一律不放行导出。
  - 启动时发现没擦完的运行，连同临时文件一起删掉，不只是置灰。
  - 也可以在 resolve 之后就登记“有新秘密”，和提前登记敏感度共用一个钩子，把时间窗口缩小（A）。

### W2 [P0] 导出读到的版本不一致（C#2 P0、A#11 P1、B#1 P0、B#8 P1）
- **问题**：
  - 导出在 IO 线程上按截止长度读文件，写线程同时可能用改名的方式重写这个文件。
  - 旧句柄读到的是擦除前的版本；重新按路径打开，长度又对不上。
  - 图片目录没有对应的截止点。
  - 清空、按容量淘汰可能在导出中途发生。
- **建议**：三路都提到最简单的做法：一期只允许导出已结束、擦除完成的运行，要导出就先停（见分歧 2）。如果仍要支持进行中导出，就要做截止快照（硬链接或句柄）、导出期间这次运行的重写排队、清空和淘汰让路。

### W8 [P1] “只记原始”的边界（A#6、B#3、C#12）
- **问题**：
  - `run_end` 的 `unfinished_tools`、`complete`、`losses`、`stop_source`、`last_round` 都是从前面的行推导出来的。其中 `stop_source` 遇到多条停止时，选哪条就是推断。
  - 请求里的字符串省略、跨记录引用，也属于有损加工。
- **建议**：
  - 写明允许的变换只有四种：序号和时间戳、确定性的结构编码、必要的脱敏、无损的压缩。
  - `run_end` 只记执行器结束时看到的状态、错误码和异常类名。
  - 第 5、7 问改为直接指向原始行。

### W10 [P1] 门槛 1 的对照方法（A#8、B#4、C#11）
- **问题**：止损开关只换掉 Recorder。三态判断、剪贴板钩子、提前登记、服务商钩子这些改动，开和关两种状态下都会执行，在这里新增的读取，两次调用序列里都会出现，门槛照样通过。用真实模型跑两次，工具调用本来就不一样。
- **建议**：用固定脚本的假模型和记录调用的假后端，拿新版本和基线 `c530ffb` 跑同一个脚本对比；代码评审加一条硬规则：记录侧不得调用 `UiObservationRegistry` 和无障碍服务的任何方法。

### W11 [P1] 请求快照（A#9、A#16、B#5、C#4）
- **问题**：
  - ChatGPT 是在 `ResponsesRequestBuilder.build` 之后，才由 `ChatGptCodexRequest.applyBody` 补写 `include`、`prompt_cache_key` 等字段（三路，已核实），方案写的记录点在这之前。
  - 非标准字符串字段被省略，第 2 问只能答一部分。
  - 引用 `attempt_end`、`tool_end` 里的内容不可靠：Responses 回放的是另存的原始输出项。
  - 差量链断了之后续不上（A）。
  - “custom body 能改掉模型和消息”只对 Chat Completions 和 Anthropic 成立。Responses 在合并之后会重新写入 model、instructions、input（A、C）。
- **建议**：记录点放在最终字符串生成的那一刻；去掉跨记录引用；怎么存见分歧 5。

### W12 [P1] 大请求体（A#10、B#5、C#9）
- **核实**：附图最多 8 张、单张 12MB、合计 32MB（`AgentRuntimeImageTransfer`），编码成 data URL 后请求体约 43MB。
- **问题**：
  - 把这么大的请求截到 2MB 再入队，JSON 就被切坏了，后面没法解析。
  - 不截的话，队列里挂着几十 MB 的字符串，写线程再整份解析，有内存溢出的风险。
- **建议**：大请求不受 2MB 入队上限约束，走单独通道；写线程流式解析（`JsonReader`），边读边把图片写成文件；单条请求设硬上限，超过就只记文字部分和图片的文件名、字节数。

### W13 [P1] 模型请求的覆盖缺口（A#16、B#6、C#6）
- **核实**：
  - `AgentContextCompactor` 调用重试器时，`onEvent` 和 `onProviderEvent` 传的都是空的。
  - `AgentFollowUpSuggester` 直接调 `provider.complete`，不经过重试器。
- **问题**：
  - 挂在 `AgentLoop` 回调上的记录点，收不到压缩请求的内容。
  - 推荐追问不在任何一次运行里，方案没说记不记；服务商那边的钩子却会照样触发。
  - 不流式的回答，思考在 `reasoning_content` 里，增量收不到，需要兜底。
  - 内容只在 `attempt_end` 时一次写下，进程中途被杀就丢了最后一段（B）。
  - 重试器取消、不可重试的失败、最后一次失败都会直接抛出，不经过 `discardAttemptReasoning`（C）。
- **建议**：
  - 记录挂在重试器内部给服务商的回调上，成功、异常、取消三种收尾都恰好写一次结束。
  - 增量按批落盘，不等到最后。
  - 推荐追问不记（不属于这次运行），写进“不做”。
  - 没有运行上下文的请求一律不记。

### W16 [P1] 字段契约（A#15、B#10、C#8）
- **问题**：
  - 很多字段缺类型、必填条件、缺失时怎么写。
  - 现有的工具结果状态有 Done、Dispatched、Backgrounded、Unknown，被折叠成 ok 之后，“已派发”看起来就像“已成功”。
  - 事件时刻是在事件发生处取，还是在写线程上取，没写。
  - `system` 只记事件名，丢掉了现有事件本来带的字段，比如网络是怎么变化的。
- **建议**：
  - 用 sealed class 补字段级定义，给出正常、重试、停止、截断、擦除、老任务各一份完整样例。
  - 工具结果保留原始状态，不折叠。
  - 时刻在事件发生处取。
  - `system` 带上现有事件已有的字段，但不为此再去查。

### W19 [P1] 容量（B#9、C#9、A#17）
- **问题**：六道上限都是直接拍的数，没有推算依据。重写时要同时占用原文件和临时文件的空间。进行中的运行不受总量约束，所以总量上限并不是硬上限。重写期间会堵住唯一的写线程。
- **建议**：开工前用 R57 类任务和最大附图量各测一次，给出典型值、P95、最坏值，再定上限；软预算和硬上限分开写。

### W20 [P1] 测试门槛（C#11、B#12、A 多处）

## 共识问题（两路提出）

- **W4 [P0；A 定 P1] 嵌套 JSON 转义（C#3、A#4）**：`tool_end.result`、请求里的 `arguments`、压缩请求的正文本身都是 JSON 文本，里面的秘密以转义形式出现：Android 自带的 org.json 会把 `/` 写成 `\/`。A 另指出，JVM 单测用的 Maven 版 org.json 不这样转义，所以门槛 3 只在 JVM 上跑，发现不了这个问题。
- **W5 [P1] 页脚承诺（A#2、C#1）**：同一个密码在被输进密码框之前，可能已经原样出现在原话、思考、提问的回答里，要等之后才会被擦。页脚应改成：“输进密码框的内容、机密工具的结果、配置的 Key 会被遮住或擦掉；你在对话里直接打出的密码、模型复述的内容、屏幕上显示的验证码会原样保存。”
- **W9 [P1] 方案新增了读取（A#7、B#4）**：查磁盘剩余空间是读设备状态，而且只为日志服务；单独读一次 `ApprovalSettings` 也是新增的读取。现有的环境快照里没有存储信息，门槛 1 的监听范围也不含这两项。
- **W15 [P1] 思考的原始类型（C#7、A#15）**：Chat Completions 的 `visibleReasoningDelta` 会把同一片里的 `reasoning.text` 和 `reasoning.summary` 拼成一个增量，一个 `source` 表达不了两种类型。
- **W17 [P1] 运行目录和停止记录（B#7、A#14）**：
  - **核实**：`MemoryDiagnostics.withRun` 在进入执行器之前就写了 `run.started`；`AgentAppState` 里有 5 处 `cancelRun`。
  - **问题**：
    - 准备阶段点停止时，运行号还没绑定，这条停止记不进日志。
    - 准备阶段那个任务的停止回调调用的是 `stopCurrentRun()`，通知栏停止会被记成“App 内停止”。
    - App 自己发来的取消消息，`sendingUid` 就是本 App 的，如果照记成外部，就重复记了一遍。
- **W18 [P1] 完整性状态（C#10、B#8）**：磁盘不可写时，往同一个文件补一行 `gap` 也写不进去；被杀的运行没有 `run_end`，也就没有完整性结论；读取时只检查两个标记，菜单上照样写“完整日志”。
- **W21 [P1] 导出控制器和止损开关（A#13、A#20、B#11）**：
  - **核实**：设置页里没有“开发者选项”；`MainActivity` 的 `configChanges` 不含屏幕方向，转屏会重建 Activity，导出就被取消了。
- **W22 [P1] 发布闭环（B#12、A#22）**：Android 12 以上，`allowBackup="false"` 挡不住设备之间的迁移，`dataExtractionRules` 必须同时写 `cloud-backup` 和 `device-transfer` 两段。
- **W24 [P2] 还能再砍（A#21、B#13、C#13，三路都提了）**：生产日志里的哈希（见 W3）、跨记录引用、2MB 入队上限、磁盘阈值、`run_end` 里的汇总字段、和 `meta` 重复的 `first_byte`。另外，§8 说“暂停继续的来源”已经砍了，§5.1 却还写着。顺手修可以拆成单独的 PR（见分歧 7）。

## 单路发现（已核实）

- **W6 [P1] 终端命令里的秘密（A#3）**：
  - **核实**：`AgentTraceFormatter.displayCommand` 会把 `API_KEY=`、`--password`、`Authorization:` 这类内容换成 `<已隐藏>`。
  - **问题**：方案的脱敏表里没有这一项，日志会原样记下命令里的令牌。
- **W7 [P1] 擦除表收得太宽（A#5）**：
  - **核实**：找不到可编辑的焦点时，`focusedInputIsPassword()` 返回空，判断就成了“不知道”；网页、自绘输入框都可能这样。
  - **问题**：
    - 网页输入的文字（大多是搜索词、地址）、判断不了的输入都进了全局擦除表，回头擦会把原话、屏幕文字、通讯录查询结果里的同一个字串一起擦掉。
    - 4–8 位的验证码进了全局表，屏幕上的“2026”“123456”也会被擦。
    - 每发现一个新值就要整份重写一次。
  - **建议**：分两级：局部遮只遮这一次调用自己的参数，包括之后请求里同一个调用 id 下的参数；全局擦只收已确认的秘密，并设长度下限或只做整词匹配；门槛 3 加反例：不是秘密的文字在运行结束后必须还在。
- **W14 [P1] 没执行到的调用丢了参数（C#5）**：
  - **核实**：`AgentToolCallValidator.normalize` 会去掉模型照着历史学来的 `redacted` 标记，所以执行时的参数不一定等于模型给的原始参数。
  - **问题**：同一批里第一个调用执行时被停止，后面的调用不会进入 `executeTool`，也就没有 `tool_start`；`attempt_end` 又只记 id 和名字，这些调用的参数就丢了。

## 分歧与待确认

1. **总结论**：A 判“有条件通过”（改完 #1–#11 再开工），B、C 判“需重大修改”。
   - **主流程倾向**：需重大修改。4 条 P0 都在擦除机制上，W11–W13 也要补设计。
   - 不过三路都认可整体结构。下面第 2、5 条的简化如果采纳，W2、W3 和 W11 的大部分会直接消失。
2. **进行中的运行能不能导出**（第 4 版时你确认过可以）：三路都建议一期只允许导出已结束、擦除完成的运行。
   - **主流程倾向**：改成只能导出已结束的运行，要导出就先停。这样 W2 一整类问题和截止点的复杂度都没有了。
   - **需要你重新定。**
3. **个人数据默认开启、Agent 能读日志目录**：
   - B 定为 P0。理由是：告知发生在采集之后，不是事先同意；没有合规审批；网页提示注入可能让 Agent 读出日志再发出去。B 建议默认关闭、首次开启前确认、拦截 Agent 读日志目录。
   - A、C 认为这是你已定的范围，不再作为问题提。
   - **主流程倾向**：保留你的决定，不加拦截。但把“记录完整日志”开关放到运行日志页上，用户自己能关，同时兼作止损开关（A#13 也这样建议）。默认开还是关，由你定。
4. **终端命令里的秘密**（A#3）：
   - 甲：把原则收窄成“只按执行时得出的敏感度遮”，并告知终端命令原样保存。
   - 乙：复用执行卡现成的打码规则，只遮这一次调用自己的命令参数。不新增读取，也不是日志自己去推断。
   - **主流程倾向**：乙。
5. **请求怎么存**：
   - A、C：存前缀差量；断链后下一条存全量；去掉跨记录引用。
   - B：一期每次都存完整的、已遮挡的请求体，压缩后存；以后量出来确实需要，再做差量。
   - **主流程倾向**：B。这样最简单，也最接近“原始”：不需要还原逻辑，不会断链，W11 的一半和 A#9 都消失了。估算一次 45 轮的任务压缩后约 1–4MB。
6. **删除对话时，删不删对应的完整日志；要不要加时间上限**（A#12）：
   - **主流程倾向**：删除对话时一并删除；不加时间上限，仍然只按 20 次保留。
7. **顺手修拆不拆出去**（A#21、B#13）：
   - **主流程倾向**：拆成单独的 PR，单独评审、单独回归。日志这边只依赖“是否密码框”的三态判断。
   - A#19 指出顺手修还有残余路径：同一批多个调用时，参数在 resolve 之前就进了检查点，进程被杀就是明文；判断不了的输入在聊天记录里仍是明文。这些留到那个 PR 里一起处理。
