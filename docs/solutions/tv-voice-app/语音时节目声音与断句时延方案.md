# 电视语音：节目声音处理与断句时延方案

- 状态：已同意并实施（2026-10-07，PR #34）
- 依据：
  - 业界调研：`.docs/tv-voice-playback/research.md`、`.docs/tv-voice-latency/research.md`
  - 10-07 TCL 电视实测：`.docs/tv-main-verify/`
- 范围：电视版语音会话期间怎么处理正在播放的节目；从用户说完到开始处理的等待时间。

## 1. 实测现状（10-07，TCL 55F295C，main `545978f`）

### 1.1 现在会暂停节目

- 语音会话一开始，`DoubaoDialogEngine` 申请 `AUDIOFOCUS_GAIN_TRANSIENT`。
- 今天 9 次会话，哔哩哔哩都在焦点申请后 40–120 ms 内暂停，会话结束才恢复。证据是系统 `dumpsys audio` 的播放器事件记录，带时间戳。
- 所以那些会话里节目声没有进入麦克风，“不循环”是暂停的结果，不是回声消除的功劳。

### 1.2 只靠回声消除，节目继续放（实验包，不申请焦点）

| 指标 | 实测 |
|---|---|
| 节目参考声（音量 16） | −63 ~ −68 dB |
| 麦克风 | −45 ~ −51 dB |
| 消除后，会话第 1 秒 | −57 ~ −59 dB（只压了约 10 dB），滤波器从零开始学 |
| 消除后，约 2 秒之后 | 多数在 −67 ~ −78 dB（压了 20–30 dB），也会出现 −55 dB 左右的尖峰 |
| 节目声被识别成话 | 6 次会话中 2 次，都在会话开始后的第 1 秒内（“北京买”和一句 7 个字的话），模型都当成提问作答 |
| 滤波器跨会话保留之后 | 4 次有效会话 0 次误识别，但其中 2 次开头仍只压了 6–12 dB。样本少，不能算解决 |
| CPU（debug 包） | 节目暂停时收音 53–56%；节目在放时 106–135% |

### 1.3 断句时延（说“退下”）

说完到会话结束共 5.9 秒：

| 段 | 耗时 | 原因 |
|---|---|---|
| 说完 → 服务端判定说完 | 1.4 秒 | `end_smooth_window_ms=1000`，加约 0.4 秒采音与传输 |
| 判定说完 → 提交 | 1.6 秒 | 电视客户端固定再等 1.5 秒（`submissionGraceMs`，因为 `localActivityDetection=false`），手机是 0.65 秒 |
| 提交 → 模型给出调用 | 2.8 秒 | 存消息、拉起执行服务、模型一轮 |

## 2. 业界做法

**节目声音**：查到的几家，没有一家让节目保持原音量继续放。“听用户说话”和“助手说话”两段，要么暂停，要么压低，回答结束后恢复。

| 做法 | 采用方 |
|---|---|
| 暂停 | AVS 交互体验指南；Fire TV（系统发 `LOSS_TRANSIENT`，应用暂停，至少静音）；Android 官方文档（语音识别示例用 `GAIN_TRANSIENT_EXCLUSIVE`，“media playback should have paused”）；百度 DCS SDK 示例 |
| 压低 | Alexa 内置电视（“the music attenuates”）；Google Nest / 投屏（电视音量降低，说完恢复）；AVS 规范允许“pause or lower” |
| 回声消除 | 各家都有。用途是外放时也能唤醒、能打断，不替代暂停或压低。HomePod：大音量时线性回声消除后，残余回声仍比人声高 10–20 dB |

**Android 9 上的压低**：
- 申请 `AUDIOFOCUS_GAIN_TRANSIENT_MAY_DUCK`，系统自动把对方压低到 0.2 倍（约 −14 dB）。
- 但对方 targetSdk ≤ 25、带 `PAUSES_ON_DUCKABLE_LOSS` 标志，或者在放语音类内容时，系统不代为压低，交给应用自己决定，应用可能压低，也可能暂停。
- 哔哩哔哩就带这个标志。
- TCL 自带的小T 用的就是 `MAY_DUCK`。今天它触发那次，哔哩哔哩没有暂停记录。

**断句**：
- 没有一家推荐“服务端判定说完后，客户端再固定等一段”。LiveKit 建议客户端额外延迟设为 0，Pipecat 原文是 “These don't stack”。
- 各家默认的总等待：Lex 0.6 秒、OpenAI 0.5 秒、LiveKit 0.3–0.5 秒、AssemblyAI 0.4 秒（没把握时最多 1.28 秒）。
- 要防一句话被切断，业界的做法是调服务端窗口或开语义判停（OpenAI semantic_vad、LiveKit、豆包 AIVAD），而不是在客户端叠加等待。

## 3. 方案

### 3.1 节目声音：压低为主，回声消除兜底

- 会话期间（听和说两段）申请 `AUDIOFOCUS_GAIN_TRANSIENT_MAY_DUCK`，用法标为 `USAGE_ASSISTANT`，会话结束后释放。
  - 系统会自动压低的应用：节目继续放，音量降到约 0.2。
  - 自己决定的应用：照它的选择，可能压低，也可能暂停。
  - 依据：Alexa 内置电视、Google Nest 的做法，以及 TCL 小T 自己的选择。
- 回声消除保留，用来消掉压低后的残余节目声，以及不理会音频焦点的应用（10-06 你遇到循环的就是这类）。
- 回声消除改进：学到的回声路径跨会话保留，每次会话只清信号缓存。实测误识别从 2/6 降到 0/4，但样本少，要在 §4 里再测。
- 不再因为“其他应用拿走焦点”就让麦克风静音、结束会话。这是 `DoubaoDialogEngine` 在 `mediaHasAudioFocus` 时的现有逻辑；压低模式下对方继续放是正常的，回答念完后的“打开 App 即结束”逻辑不受影响。

备选是**维持暂停**，即现状。这和 AVS 交互体验指南、Fire TV 的要求一致，最稳。代价是每次说话都会打断节目。你之前否决过暂停，所以这里推荐压低。

### 3.2 断句：只等一处

- 电视客户端固定的 1.5 秒额外等待，改为和手机一样的 0.65 秒，约省 0.85 秒。
- 再核实 `end_smooth_window_ms=1000` 在服务端是否真的生效：火山文档写默认 1500，又没说清需不需要配合 `enable_custom_vad`。
- 这一期不缩短服务端窗口，也不开语义判停（AIVAD）。等上一条落地、实测截断率之后再定。

## 4. 验证（电视实测，需要你安排时间）

| 项 | 做法 | 达标线 |
|---|---|---|
| 压低效果 | 哔哩哔哩、腾讯视频、爱奇艺、优酷、电视直播各测一次唤醒。看系统播放器事件（暂停 / 继续），看会话期间麦克风电平比会话前降了多少 | 逐个记录每个应用是压低还是暂停 |
| 误识别 | 节目在放，每个应用唤醒后不说话各 10 次 | 0 次误识别 |
| 能听清 | 节目在放，每个应用说 10 句正常指令 | 至少 9 句识别正确 |
| 截断 | 说中间有停顿的长句 10 句（如“帮我找一下……那个……周星驰的电影”） | 至少 9 句不被切成两句 |
| 断句时延 | 说完到提交 | 比现在的 3.0 秒少约 0.85 秒 |
| CPU | 正式包，节目在放时收音 | 记录数值 |

电平诊断（每秒记一次参考声、麦克风、消除后的电平）这次保留在正式代码里，只在语音会话期间记，用来做上面的验收和以后排查问题。
